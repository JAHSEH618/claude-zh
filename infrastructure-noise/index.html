量化 agentic coding eval 中的基础设施噪声

Published Feb 05, 2026Anthropic Research

基础设施配置的差异能让 agentic coding benchmark 的分数波动好几个百分点——有时比榜单上头部模型之间的差距还大。

SWE-bench、Terminal-Bench 这类 agentic coding benchmark 常被用来比较前沿模型的软件工程能力——榜单头几名之间往往只差几个百分点。这些分数常被当作模型相对能力的精确度量，并越来越多地影响部署选型的决策。但我们的实验发现，仅基础设施配置一项就能造成超出这些差距的波动。在内部实验中，Terminal-Bench 2.0 上资源最充足与最紧张的两套环境，分数相差 6 个百分点（p < 0.01）。

静态 benchmark 直接给模型的输出打分——运行环境不参与结果。Agentic coding eval 不一样：模型处在一个完整的环境里，要写程序、跑测试、装依赖、多轮迭代。运行时从被动的容器变成了解题过程的组成部分。资源预算和时间限制不同的两个 agent，考的根本不是同一份卷子。

Eval 开发者开始正视这一点。比如 Terminal-Bench 在最新的 2.0 版本里按任务逐个给出了推荐的 CPU 和内存配置。但把配置写出来和把配置稳定执行下去是两回事。而且我们发现，执行方式本身会改变 benchmark 实际测到的东西。

事情的起因

我们在 Google Kubernetes Engine 集群上跑 Terminal-Bench 2.0。校准环境时注意到，我们的分数对不上官方 leaderboard，基础设施错误率还高得反常：多达 6% 的任务因为 pod 报错而失败，其中大多数和模型解题能力无关。

分数差异出在执行方式上。我们的 Kubernetes 实现把按任务配置的资源规格同时当作下限和硬上限：容器保证拿到指定资源，但一旦超出就立刻被杀。容器运行时通过两个独立参数管控资源：预留分配（事先划给容器的资源）和硬限额（超过就杀容器）。两者设成同一个值时，瞬态尖峰就完全没有余量：一次短暂的内存波动就足以 OOM 掉一个本可以跑通的容器。Terminal-Bench 的 leaderboard 用的是另一个 sandbox 供应商，实现更宽松，允许临时超额分配而不终止容器，以此优先保证基础设施稳定。

这个发现引出了一个更大的问题：资源配置究竟多大程度影响 eval 分数？

为了量化 scaffold 的影响，我们在六种资源配置下跑了 Terminal-Bench 2.0：从严格执行按任务规格（1x，规格同时作下限和上限）到完全不设上限。其余全部保持不变：同一个 Claude 模型、同一套 harness、同一批任务。

实验中，成功率随资源余量增加而上升。主要驱动力是基础设施错误率逐级单调下降：从严格执行时的 5.8% 降到不设上限时的 0.5%。从严格执行到 3x 余量（5.8% 到 2.1%）的下降在 p < 0.001 水平上显著。余量越大，因超分配被杀的容器越少。

1x 到 3x 之间，成功率在噪声范围内波动（p=0.40）。1x 下崩溃的大部分任务，换个配置大概率也过不了——数据里能看到这一点：agent 探索、撞上资源墙、被抢占，但它本来就没走上通往正确答案的路。

大约从 3x 开始，趋势变了：成功率上升的速度快过基础设施错误率下降的速度。

3x 到不设上限之间，基础设施错误率再降 1.6 个百分点，成功率却几乎涨了 4 个百分点。多出来的资源让 agent 能尝试那些只在宽裕分配下可行的路径：拉大型依赖、启动开销很大的子进程、跑高内存占用的测试套件。不设上限时，相对 1x 的总提升是 +6 个百分点（p < 0.01）。处在临界状态的任务，比如 rstan-to-pystan 和 compile-compcert，在拿到内存余量后成功率显著改善。

这对测量的影响

大致到 Terminal-Bench 规格的 3x 以内，多出来的资源只是修复基础设施可靠性问题，即瞬态资源尖峰。Terminal-Bench 维护者用的 sandbox 供应商在幕后就隐式地做了这件事：eval 变得更稳定，但没有变得更简单。

超过 3x 之后，多出来的资源开始帮 agent 解决它之前解不出的问题——限制条件会实实在在地改变 eval 测到的东西。紧的限制无意间奖励效率极高的策略；宽的限制更宽容，奖励的是能更好利用所有可用资源的 agent。

快速写出精简高效代码的 agent 在紧约束下占优；用重型工具暴力求解的 agent 在宽约束下占优。两者都是合理的测量对象，但如果不注明资源配置就把它们压进同一个分数，分数之间的差异——以及向真实场景的泛化性——就很难解读。

以 bn-fit-modify 为例，这是个要求拟合贝叶斯网络的 Terminal-Bench 任务。一些模型的第一步是装标准 Python 数据科学全家桶：pandas、networkx、scikit-learn, 连同整条工具链。宽限制下这套流程能跑通；紧限制下，pod 在安装阶段就内存耗尽，agent 一行解题代码都还没写。更省的策略是存在的（只用标准库从零实现数学部分），有些模型默认就走这条路，另一些不。不同模型的默认策略不同，而资源配置决定了哪种策略碰巧能成。我们在 Anthropic 的不同模型上复现了核心结论：效应方向一致，幅度有差异。同样的趋势在其他非 Claude 模型上似乎也成立，但我们没做过严格验证。

我们还测试了这个模式在 Terminal-Bench 之外的 eval 上是否成立，在 SWE-bench 上跑了交叉实验：227 道题，每题 10 个样本，总可用内存从基线拉到 5x。同样的效应存在，只是幅度更小：分数依旧随内存单调上升，但 5x 只比 1x 高 1.54 个百分点。SWE-bench 任务对资源的消耗更低，效应小一些符合预期，但它说明内存分配在那里同样不是中性的。

其他方差来源

资源分配不是唯一的隐藏变量。在某些配置下，时间限制也开始起作用。

原则上，评测环境的每个环节都可能影响最终分数：集群健康度、硬件规格、并发度，甚至出口带宽。Agentic eval 天生就是端到端系统测试，系统里任何组件都可能成为混杂变量。我们观察到一些非正式的证据：通过率随一天中的时间波动，可能是因为 API 延迟随流量模式和故障事件变化。我们没正式量化过这个效应，但它说明了一个更大的问题：“模型能力”和“基础设施行为”之间的界限，比单个 benchmark 分数暗示的要模糊得多。模型供应商可以用专用硬件把评测基础设施隔离出来，外部评测机构却很难做到。

公开 benchmark 本意是测纯粹的模型能力，但实践中很容易把基础设施的特性混进来。有时候这反而是想要的——可以对整个技术栈做端到端测试，但更多时候不是。对于打算公开分享的 coding eval，在多个时段、多天各跑一轮，有助于把噪声平均掉。

我们的建议

理想情况是每轮 eval 都在完全相同的硬件条件下运行——跑 eval 的 scaffold 和推理栈都一样——这样能确保全程完美可复现。但这未必总可行。

考虑到容器运行时管控资源的方式——预留分配加一个独立的硬杀阈值——我们建议 eval 按任务同时指定这两个参数，而不是只钉一个值。只给一个精确规格，等于把预留分配和杀阈值设成一样，余量为零：我们在 1x 下记录到的那些瞬态内存尖峰，足以让 eval 失稳。把两个参数分开，既能给容器足够的呼吸空间、避免误 OOM，又能保留硬上限，防止分数虚高。

两者之间的区间要校准到位：下限和上限跑出的分数应落在彼此的噪声范围内。比如 Terminal-Bench 2.0 里，把上限设为按任务规格的 3x，基础设施错误率大约砍掉三分之二（5.8% 到 2.1%，p < 0.001），同时分数提升不大且远在噪声之内（p = 0.40）。这是个合理的取舍：基础设施混杂变量基本被中和，又有意义的资源压力没有消失。具体倍数会因 benchmark 和任务分布而异，应当报告出来，但用实验校准区间这个原则是通用的。

我们为什么在意

这些发现的实际影响超出 eval 基础设施本身。Benchmark 分数越来越多地进入决策流程，但关注度（和依赖度）的提升并没有始终带来运行与报告方式的相应严谨。照目前的情况，榜单上 2 分的领先可能来自真实的能力差距，也可能来自某轮 eval 跑在更强的硬件上，或者碰上了更走运的时段，或者两者都有。在环境配置被公开（或标准化）之前，外界很难分辨，除非相关方愿意多做一步，在相同条件下复现客观结果。

对 Anthropic 这样的实验室，含义是：agentic eval 的资源配置应当被当作一等实验变量，用和 prompt 格式、采样温度同样的严谨程度来记录与控制。对 benchmark 维护者，公开推荐资源配置（像 Terminal-Bench 2.0 那样）已经很有价值，再写明执行方法，就能补上我们识别出的缺口。对任何使用 benchmark 结果的人，要点是：agentic eval 上的小分差带有的不确定性，比报告数字的精度所暗示的大得多——尤其是一些混杂变量很难控制。

在资源方法论被标准化之前，我们的数据提示：在 eval 配置被完整记录并对齐之前，榜单上 3 个百分点以内的差距都值得打折扣看待。Terminal-Bench 在中等幅度的资源配置范围内，观察到的分数跨度略低于 2 个百分点。朴素的二项分布置信区间本身就有 1-2 个百分点宽；我们在这里记录的基础设施混杂变量叠加在这个区间之上，而不是落在区间之内。在分配区间的两端，跨度达到 6。

几分领先可能意味着真实的能力差距——也可能只是别人的 VM 更大。
