构建 Claude Code 的教训：Prompt caching 就是一切

Apr 30, 2026Claude Code Blog约 6 minThariq Shihipar

在 Claude Code 里优化 prompt caching 的最佳实践，包括怎么最有效地组织你的 prompt、使用工具、以及叠加 compaction。

工程里常说"cache rules everything around me"，同样的规则对 agent 也成立。

像 Claude Code 这样长时间运行的 agentic 产品，靠 prompt caching 才可行——它让我们复用之前 roundtrip 的计算，显著降低延迟和成本。

在 Claude Code，我们整个 harness 都围绕 prompt caching 构建。高 prompt cache 命中率降低成本，也帮我们为订阅计划创建更宽松的 rate limit，所以我们对 prompt cache 命中率跑告警，如果太低就宣布 SEV。

这些是我们在大规模优化 prompt caching 中（常常反直觉地）学到的教训。

为你的 prompt 按缓存布局

Prompt caching 靠前缀匹配工作——API 缓存从请求开头到每个 cache_control 断点之间的所有内容。这意味着你放东西的顺序极其重要，你希望尽可能多的请求共享前缀。

你怎么组织 prompt 对输出质量也重要，不只是缓存命中——prompt engineering 基础是这个纪律的另一半。

最好的做法是静态内容在前、动态内容在后。对 Claude Code 这看起来像：

  • 静态 system prompt & 工具（全局缓存）
  • CLAUDE.md（项目内缓存）
  • Session context（session 内缓存）
  • 对话消息

    • 这样我们最大化多少 session 共享缓存命中。

    但这个 approach 可以出人意料地脆弱。我们过去因为各种原因破坏过这个顺序，包括：在静态 system prompt 里放一个带秒的时间戳、非确定性地乱序工具定义、更新工具参数（比如 Agent 工具能调用哪些 agent）。

    用 messages 做更新

    有时你放进 prompt 的信息会过期，比如时间，或用户改了一个文件。更新 prompt 可能很诱人，但那会导致 cache miss，对用户可能相当贵。

    考虑能不能在 agent 下一个 turn 里通过 message 传入这份信息。在 Claude Code，我们在下一条 user message 或 tool result 里加一个 <system-reminder> 标签，带上给模型的更新信息，这有助于保持缓存。

    不要在 session 中途换模型

    Prompt cache 是特定于模型的，这让 prompt caching 的数学相当反直觉。

    比如，如果你和 Opus 的对话已经 100k token 了，想问一个相当容易回答的问题，切到 Haiku 实际上会比让 Opus 回答更贵，因为我们得为 Haiku 重建 prompt cache。

    如果你需要换模型，最好的方式是用 subagents；扩展上面的例子，你可以部署一个 subagent，prompt Opus 为还需要完成的另一个模型准备一条"hand-off"消息。我们经常用 Haiku 的 Claude Code Explore agents 做这个。

    绝不在 session 中途增删工具

    在对话中途改工具集是人们破坏 prompt caching 最常见的方式之一。它看起来直觉——你应该只给模型你认为它现在需要的工具。但因为工具是缓存前缀的一部分，增删一个工具会让整个对话的缓存失效。

    用 Plan Mode 围绕缓存设计

    Plan Mode 是围绕缓存约束设计功能的好例子。直觉的方式是：用户进入 plan mode 时，把工具集换成只含只读工具，但那会破坏缓存。

    反过来，我们始终在请求里保留全部工具，并把 EnterPlanMode 和 ExitPlanMode 作为工具本身。当用户打开 Plan Mode，agent 收到一条 system message，解释它处于 Plan Mode 以及指令是什么：探索代码库、别编辑文件、plan 完成时调用 ExitPlanMode。工具定义从不改变。

    这有一个附带好处：因为 EnterPlanMode 是模型可以自己调用的工具，当它检测到难问题时，它可以自主进入 plan mode，没有任何 cache 破坏。

    用 tool search 延迟而不是移除

    同样的原则适用于我们的 tool search 工具。Claude Code 可能加载几十个 MCP 工具，每个请求都包含它们全部会很贵，但对话中途移除会破坏缓存。

    我们的方案：defer_loading。不删工具，我们发送轻量 stub（只有工具名，带 defer_loading: true），模型在需要时可以通过 tool search"发现"它们。完整工具 schema 只在模型选中它们时加载。这让缓存前缀保持稳定，因为同样的 stub 总以同样的顺序存在。

    你还可以通过我们的 API 用 tool search 工具来简化这个。

    压缩而不破坏缓存

    Compaction 是当你用尽 context window 时发生的事。我们总结到现在的对话，用那个摘要继续一个新 session。

    Compaction 和 prompt caching 的交互很容易做错。要压缩一个对话，你必须把完整对话发给模型让它写摘要。最简单的做法是单独一个 API 调用，带自己的 system prompt（像"总结这个"）和不带工具，但那正是成本陷阱所在。Prompt caching 只在请求前缀从开头字节级匹配已缓存内容时才适用。你的主对话在某个 system prompt 和工具集下缓存；总结调用用不同的 system prompt 和没有工具，所以前缀从第一个 token 就分叉，缓存一点都不适用。你为整个发进去的对话支付完整的未缓存输入价——而且对话越长（也就是你越需要先做 compaction），那一个调用就越贵。

    方案：cache-safe forking

    我们做 compaction 时，用完全相同的 system prompt、user context、system context 和工具定义，跟父对话一样。我们把父对话的消息前置，然后在末尾追加 compaction prompt 作为新的 user message。

    从 API 的角度，这个请求看起来和父请求最后一次几乎一样——同样的前缀、同样的工具、同样的历史——所以缓存前缀被复用。唯一的新 token 是 compaction prompt 本身。

    不过这也意味着我们需要保存一个"compaction buffer"，好在 context window 里有足够空间容纳压缩消息和摘要输出的 token。

    Compaction 棘手，但幸运的是，你不需要自己学这些教训——基于我们从 Claude Code 的所学，我们把 compaction 直接建进了 API，所以你可以在自己的应用里应用这些 pattern。

    学到的教训

    以下是我们在构建 agent 时优化 prompt caching 发现的几个有用 pattern：

  • Prompt caching 是前缀匹配。前缀里任何地方的任何改动都会让其后一切失效。围绕这个约束设计你的整个系统。顺序对了，大部分缓存免费工作。
  • 用 messages 代替改 system prompt。你可能会想编辑 system prompt 来做进入 plan mode、改日期等事，但把这些插进对话中的 messages 其实更好。
  • 别在对话中途改工具或模型。用工具来建模状态转移（像 plan mode），而不是改工具集。延迟加载工具，而不是删工具。
  • 像监控 uptime 一样监控你的缓存命中率。我们对 cache 破坏告警，把它们当事故。几个百分点的 cache miss 率可以剧烈影响成本和延迟。
  • Fork 操作需要共享父的前缀。如果你需要跑一个旁路计算（compaction、总结、skill 执行），用相同的 cache-safe 参数，这样你在父的前缀上拿到缓存命中。

    • Claude Code 从第一天起就围绕 prompt caching 构建；为了构建 agent 拿到最好结果，我们建议你也这么做。
