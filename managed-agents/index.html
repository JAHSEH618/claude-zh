规模化 Managed Agents：把大脑和双手解耦

Published Apr 08, 2026Anthropic Research

Harness 里编码着各种假设，模型一旦进步，这些假设就会过时。Managed Agents——我们面向长周期 agent 任务的托管服务——围绕一组接口构建，harness 再怎么变，接口保持稳定。

按照我们的 文档，即可开始使用 Claude Managed Agents。

Engineering Blog 上反复出现的一个话题，是如何为长周期任务构建有效的 agent、设计 harness，以及长周期任务。这些工作有一条共同主线：harness 编码了 Claude 独自做不到什么的假设。但模型在进步，这些假设会随之过时，需要经常被重新检验。

举个具体的例子。在此前的工作中，我们发现 Claude Sonnet 4.5 在察觉 context 上限快到时，会提前收工，这种行为有时被称为 "context anxiety"。我们的应对是在 harness 里加入 context reset。但同样的 harness 用在 Claude Opus 4.5 上时，这种行为消失了，reset 变成了累赘。

我们预期 harness 还会持续演进。于是我们构建了 Managed Agents：Claude Platform 里的一个托管服务，替你运行长周期 agent，只经过一小撮接口，而这些接口的设计目标是比任何具体实现活得更久——包括我们今天要跑的那些。

构建 Managed Agents 意味着要解决计算机科学里的一个老问题：如何为"尚未被想到的程序"设计系统。几十年前，操作系统靠把硬件虚拟成抽象——process、file——解决了这个问题，这些抽象足够通用，能罩住当时还不存在的程序。抽象的寿命超过了硬件：read() 命令根本不关心自己访问的是 1970 年代的 disk pack 还是现代 SSD。上层抽象保持稳定，下层实现自由变化。

Managed Agents 沿用同样的模式。我们把 agent 的组件虚拟化成了三类：session（只追加、记录所有一切事件的日志）、harness（调用 Claude、并把 Claude 的 tool call 路由到相应基础设施的那个循环）、sandbox（Claude 可以跑代码、改文件的执行环境）。这样，每个组件的实现都可以单独更换，不影响其他组件。我们对这些接口的形状有自己的主张，但对接口背后跑什么没有主张。

别养宠物

我们最初的方案是把所有 agent 组件塞进同一个容器：session、agent harness、sandbox 共享同一套环境。这种做法有好处，比如文件编辑就是直接的 syscall，也不用设计服务边界。

但把所有东西耦合进一个容器，撞上了一个老基础设施问题：我们收养了一只宠物。在 pets-vs-cattle 的类比里，宠物是有名字、手把手照顾、丢了受不了的个体，家畜则可以互相替换。在我们的场景里，服务器就成了那只宠物：容器一挂，session 就没了；容器一卡死，我们得想办法把它救活。

给容器"治病"就是给卡死的 session 排障。我们唯一的入口是 WebSocket 事件流，但它说不出故障发生在哪：harness 里的 bug、事件流丢包、容器掉线，表现出来全是一个样。想搞清楚哪里出了问题，工程师得进容器开 shell，可容器里往往还装着用户数据，这条路基本等于没有调试能力。

第二个问题是，harness 假设 Claude 处理的一切都在它所在的容器里。客户想让我们把 Claude 接到他们的 VPC 时，要么把他们的网络跟我们的做 peering，要么在他们的环境里跑我们的 harness。烧进 harness 的假设，在我们要把它接到别的基础设施时，变成了麻烦。

把大脑和双手解耦

我们最后得出的方案是：把我们理解的"大脑"（Claude 和它的 harness）从"双手"（执行动作的 sandbox 和工具）和"session"（session 事件日志）两边都解耦出来。每一方都变成一个对其他方假设很少的接口，每一方都可以独立失败、独立替换。

Harness 离开容器。大脑和双手解耦，意味着 harness 不再住在容器里。它调用容器，跟调用任何其他工具一个方式：execute(name, input) → string。容器变成了家畜。容器挂了，harness 把这次失败当作 tool call 错误接住，传回给 Claude。Claude 要是决定重试，就用标准配方重新初始化一个新容器：provision({resources})。我们再也不用去救活挂掉的容器了。

从 harness 故障中恢复。Harness 也变成了家畜。session 日志在 harness 之外，harness 里的任何东西都不需要扛过崩溃。一个 harness 挂了，就用 wake(sessionId) 拉起一个新的，用 getSession(id) 把事件日志拿回来，从最后一个事件接着跑。agent 循环期间，harness 通过 emitEvent(id, event) 写 session，把事件留成持久记录。

安全边界。在耦合设计里，Claude 生成的任何不可信代码都跟 credentials 跑在同一个容器里——一次 prompt injection 只要说服 Claude 读一下自己的环境就行。攻击者拿到那些 token，就能开出全新的、不受限的 session，把活儿委托过去。收窄 token 权限范围是明面上的缓解手段，但它编码了一个假设：Claude 拿不到完整 token 就做不了事——而 Claude 正变得越来越聪明。结构性的修法是：确保 token 从 Claude 生成代码所运行的 sandbox 永远够不到。

我们用了两种模式来保证这一点。认证信息可以跟资源捆绑在一起，也可以放在 sandbox 外的 vault 里。Git 的做法是：sandbox 初始化时用各个仓库的 access token 把仓库 clone 下来，接进本地 git remote。之后在 sandbox 内 git push、pull 正常用，agent 从头到尾不碰 token 本身。自定义工具走 MCP，OAuth token 存在安全 vault 里。Claude 通过专用代理调用 MCP 工具，代理接收一个跟 session 关联的 token，从 vault 取出对应的 credentials 去调外部服务。harness 全程不知道任何 credentials 的存在。

Session 不是 Claude 的 context window

长周期任务常常超过 Claude context window 的长度，而标准的应对手段都要做一个不可逆的决定：留什么。这些技术在我们在 context engineering 上的此前工作里探索过。比如，compaction 让 Claude 把 context window 存成摘要，memory 工具让 Claude 把 context 写进文件，实现跨 session 的学习。这还可以配合 context trimming，选择性地删掉一些 token，比如旧的 tool result 或 thinking block。

但"选择保留或丢弃 context"这种不可逆决定会导致失败。未来的 turn 需要哪些 token，很难提前知道。如果消息被 compaction 步骤改写，harness 会把压缩后的消息从 Claude 的 context window 里删掉，这些消息只有在存下来的情况下才能找回。此前的工作探索过一种应对：把 context 存成活在 context window 之外的对象。比如，context 可以是 REPL 里的一个对象，LLM 通过写代码对它做 filter 或 slice 来访问。

在 Managed Agents 里，session 提供同样的能力：一个活在 Claude context window 之外的 context 对象。但 context 不放在 sandbox 或 REPL 里，而是持久地存在 session 日志里。接口 getEvents(), 让大脑可以按位置选取事件流的切片来盘问 context。这个接口用法很灵活：大脑可以从上次停下的地方接着读，可以回退到某个时刻之前几个事件看前因，也可以在某个动作之前把相关 context 重读一遍。

取回的事件还可以先经过 harness 的变换，再进 Claude 的 context window。变换的内容由 harness 自己决定，包括为提高 prompt cache 命中率而做的 context 组织，以及 context engineering。我们把两件事分开：可恢复的 context 存储放在 session，任意的 context 管理放在 harness。因为我们无法预测未来的模型需要什么样的具体 context engineering。接口把 context 管理推给 harness，只保证 session 是持久的、可以被盘问的。


多个大脑，多双手

多个大脑。大脑和双手解耦，解决的是我们最早一批客户抱怨里的一条。团队想让 Claude 操作自己 VPC 里的资源时，唯一的路径是把他们的网络跟我们的做 peering，因为装着 harness 的容器假设所有资源都紧挨着它。harness 离开容器后，这个假设就不存在了。同一个改动还带来了性能收益。一开始我们把大脑放进容器，意味着多个大脑就需要同样多个容器。对每个大脑来说，容器没 provision 好之前推理一步都跑不了，每个 session 都得先付全额的容器初始化成本。每个 session——哪怕永远不会碰 sandbox——都得 clone 仓库、拉起进程、从我们的服务器拉取待处理事件。

这段空等时间体现在 time-to-first-token（TTFT）上，它度量一个 session 从接到任务到产出第一个 response token 等了多久。TTFT 是用户感受最直接的延迟。

大脑和双手解耦后，容器只在需要时才由大脑通过一次 tool call (execute(name, input) → string) 来 provision。一个暂时不需要容器的 session 就不用等容器。编排层从 session 日志里拉出待处理事件，推理就能立刻开始。采用这套架构后，我们的 p50 TTFT 降了大约 60%，p95 降了 90% 以上。扩展到多个大脑，就是启动多个无状态 harness，只在需要时才把它们连上手。

多双手。我们还希望每个大脑能连上多双手。实际含义是，Claude 必须在多个执行环境之间推理、决定把活儿发到哪里——这比在单个 shell 里操作认知要求更高。最初把大脑放在单个容器里，是因为早期的模型做不到这一点。随着模型能力增长，单容器反过来成了限制：那个容器一挂，大脑正在伸进去的每一双手的状态全丢。

大脑和双手解耦后，每双手都变成了一个工具 execute(name, input) → string：进去一个名字和 input，出来一个 string。这个接口支持任何自定义工具、任何 MCP server，也支持我们自己的工具。harness 不知道那个 sandbox 是容器、手机，还是宝可梦模拟器。而且没有任何一双手跟某个大脑绑死，大脑之间可以把手传给别人。

结论

我们面对的挑战是个老问题：如何为"尚未被想到的程序"设计系统。操作系统靠把硬件虚拟成足够通用的抽象、罩住当时还不存在的程序，撑了几十年。Managed Agents 想做的，是一个能容纳未来 Claude 周围的 harness、sandbox 或其他组件的系统。

Managed Agents 是同一精神的 meta-harness，对 Claude 未来需要哪个具体的 harness 没有主张。它是一套通用接口的系统，能容纳很多不同的 harness。比如，Claude Code 就是一个出色的 harness，我们在各类任务中广泛使用。我们也展示过，面向特定任务的 agent harness 在狭窄领域里表现优异。Managed Agents 能容纳其中任何一个，随时间的推移跟上 Claude 智能的增长。

meta-harness 设计意味着对 Claude 周围的接口有主张：我们预期 Claude 需要操作状态（session）和执行计算（sandbox）的能力，也需要扩展到多脑多手的能力。接口被设计成可以长期可靠、安全地运行。但我们对 Claude 需要多少大脑和手、它们在哪里，不做任何假设。
