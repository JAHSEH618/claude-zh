用一组并行 Claude 构建 C 编译器

Published Feb 05, 2026Anthropic Research

我们用 agent teams 让 Opus 4.6 构建一个 C 编译器，然后（基本）走开了。它让我们对自主软件开发的未来有了新的认识。

作者 Nicholas Carlini，我们 Safeguards 团队的研究员。

我一直在试验一种监督语言模型的新方法，我们称之为 "agent teams"。

在 agent teams 里，多个 Claude 实例在共享的代码库上并行工作，整个过程不需要人工实时参与。这种方法大幅扩展了 LLM agent 能完成的事的范围。

为了压力测试它，我让 16 个 agent 从零开始写一个基于 Rust 的 C 编译器，要求能编译 Linux 内核。经过近 2,000 次 Claude Code 会话、$20,000 的 API 开销，这支 agent 团队产出了一个 100,000 行的编译器，能在 x86、ARM 和 RISC-V 上构建 Linux 6.9。

这个编译器本身就是一个有意思的产物，但我在这里想聊的是我为长时间运行的自主 agent 团队设计 harness 的收获：怎么写测试让 agent 在无人监督时保持正轨，怎么组织工作让多个 agent 并行推进，以及这种方法在哪里触顶。

让 Claude 长时间运行

现有的 agent scaffold（比如 Claude Code）都要求操作者在线，并能随时参与协作。让它解决一个耗时且复杂的问题时，模型也许能解决一部分，但最终总会停下来等待进一步输入——一个问题、一次状态更新，或一个澄清请求。

想要 Claude 持续自主地推进，我搭了一个 harness，把 Claude 塞进一个简单的循环（如果你见过 Ralph-loop，这看着眼熟）。它做完一个任务就立刻接下一个。（在容器里跑，别在你的真机上跑。）


在 agent prompt 里，我告诉 Claude 要解决什么问题，并要求它把问题拆成小块来推进：跟踪自己正在做什么，想清楚下一步做什么，然后一直做到完美为止。（关于最后一点，Claude 没有选择余地。循环是永远跑的——不过有一次，我看到 Claude 不小心执行了 pkill -9 bash，把自己杀了，循环也就结束了。哎呀！）


并行运行 Claude

并行运行多个实例可以弥补单 agent harness 的两个短板：

  • 一个 Claude Code 会话一次只能做一件事。尤其是随着项目范围扩大，并行调试多个问题效率高得多。
  • 多个 Claude agent 还能分工。几个 agent 负责解决眼前的实际问题，其他专门的 agent 可以被调用来（比如）维护文档、把关代码质量，或处理专门的子任务。

    • 我的并行 Claude 实现非常精简。先建一个新的 bare git repo，为每个 agent 拉起一个 Docker 容器，把仓库挂载到 /upstream。每个 agent 把仓库克隆一份本地副本到 /workspace，做完之后从自己的容器 push 到 upstream。

    为了防止两个 agent 同时去解决同一个问题，harness 用一个简单的同步算法：

  • Claude 通过往 current_tasks/ 里写一个文本文件来给任务上"锁"（比如一个 agent 可能锁 current_tasks/parse_if_statement.txt，另一个锁 current_tasks/codegen_function_definition.txt）。如果两个 agent 想认领同一个任务，git 的同步机制会逼着第二个 agent 换个任务。
  • Claude 做完任务，从 upstream pull，合并其他 agent 的改动，push 自己的改动，然后移除锁。合并冲突很常见，但 Claude 足够聪明，能自己搞定。
  • agent 生成循环没有尽头：它在全新容器里生成一个新的 Claude Code 会话，然后一切重来。

    • 这只是一个非常早期的研究原型。我还没有实现 agent 之间的其他通信方式，也没有强制任何管理高层目标的过程。我不使用编排 agent。

    相反，我把怎么行动的决定权交给每个 Claude agent。大多数情况下，Claude 会挑"next most obvious"的问题去做。卡在某个 bug 上时，Claude 往往会维护一份持续更新的文档，记录失败的方法和剩余任务。在项目的 git 仓库 里，你可以翻阅提交历史，看它去领取各种任务的锁。

    和 Claude agent 团队编程的经验

    scaffold 让 Claude 在循环里跑，但这个循环只有在 Claude 知道如何推进时才有用。我花的大部分精力在围绕 Claude 设计环境上——测试、环境、反馈——让它在我缺席时也能自己摸清状况。下面是我觉得最管用的做法。

    写出质量极高的测试

    Claude 会自主地解决我交给它的任何问题。所以任务验证器必须接近完美，否则 Claude 会去解一个错误的问题。改进测试 harness 需要找到高质量的编译器测试集，为开源软件包写验证器和构建脚本，还要盯着 Claude 在犯什么错，每识别出一种失败模式就设计新测试。

    比如，项目后期，Claude 每实现一个新功能就经常把现有功能弄坏。为了解决这个问题，我搭了一条持续集成流水线，并加了更严格的强制检查，让 Claude 能更好地测试自己的工作，使新提交无法破坏现有代码。

    站在 Claude 的角度

    我得不断提醒自己，这个测试 harness 是给 Claude 写的，不是给我自己写的，这意味着要重新审视很多关于测试该如何传达结果的假设。

    比如，每个 agent 都被丢进一个没有任何上下文的新容器，要花不少时间搞清楚状况，尤其是在大项目上。还没走到测试这一步，为了让 Claude 能自助，我在指令里要求它维护详尽的 README 和进度文件，并频繁更新当前状态。

    我也始终考虑到语言模型有固有的局限，在这个项目里必须绕着这些局限来做设计。包括：

  • Context window 污染：测试 harness 不应该打印成千上万的无用字节。最多打印几行输出，把所有重要信息写进日志文件，让 Claude 需要时能查到。日志文件要方便自动处理：有错误时，Claude 应该写 ERROR 并把原因放在同一行，这样 grep 就能找到。最好预先算好汇总统计，这样 Claude 就不用自己重算。
  • 时间盲区：Claude 没有时间感，放任不管的话，它会心甘情愿地花几个小时跑测试，而不是推进工作。harness 只在很少的时候打印增量进度（避免污染 context），并内置一个默认的 --fast 选项，只跑 1% 或 10% 的随机抽样。这个抽样对每个 agent 是确定的，但在不同 VM 之间是随机的，所以 Claude 整体仍覆盖所有文件，而每个 agent 都能精确识别出回归问题。

    • 让并行容易起来

    当有很多互不相同的失败测试时，并行化就很简单：每个 agent 挑一个不同的失败测试来做。测试集通过率达到 99% 之后，每个 agent 各负责让一个不同的小型开源项目（比如 SQlite、Redis、libjpeg、MQuickJS、Lua）编译通过。

    但当 agent 们开始编译 Linux 内核时，它们卡住了。编译 Linux 内核和几百个独立测试的测试集不同，它是一整块巨大的任务。每个 agent 都会撞到同一个 bug，修掉那个 bug，然后又把彼此的改动覆盖掉。跑 16 个 agent 没用，因为每个都卡在同一个任务上。

    解决办法是把 GCC 当作一个在线的、已知可用的编译器 oracle 来做对比。我写了个新的测试 harness：随机让 GCC 编译内核的大部分文件，只用 Claude 的 C 编译器编译剩下的文件。如果内核能跑，说明问题不在 Claude 负责的那部分文件里；如果跑不了，就用 GCC 重编其中一些文件来进一步缩小范围。这样每个 agent 就能并行工作，在不同文件里修不同的 bug，直到 Claude 的编译器最终能编译所有文件。（这套方法跑通之后，还需要用 delta debugging 技巧找出那些单独能过、放在一起就失败的文件对。）

    多个 agent 角色

    并行也带来了分工。LLM 写的代码经常重复实现已有功能，所以我派一个 agent 专门合并它发现的重复代码。另一个负责提升编译器本身的性能，第三个负责让编译产出的代码更高效。我还让一个 agent 以 Rust 开发者的视角评审项目设计，并对项目做结构性调整以提升整体代码质量，另一个负责文档。

    压力测试 agent 团队的极限

    这个项目被设计成一个能力 benchmark。我感兴趣的是压力测试 LLM 眼下勉强能做到的边界，好让我们为模型未来能可靠做到的事情做好准备。

    我一直用 C Compiler 项目作为整个 Claude 4 模型系列的 benchmark。和之前几个项目一样，我先写下我想要什么：一个从零开始写的、无依赖的优化编译器，兼容 GCC，能编译 Linux 内核，并设计成支持多个 backend。我指定了设计的一些方面（比如要有 SSA IR 以支持多轮优化 pass），但没有细化到具体怎么做。

    之前的 Opus 4 模型几乎造不出能用的编译器。Opus 4.5 是第一个越过这道门槛的：它能做出一个能跑过大型测试集的可用编译器，但仍然编译不了任何真实的大型项目。我对 Opus 4.6 的目标还是测试极限。

    评估

    两周内近 2,000 次 Claude Code 会话里，Opus 4.6 消耗了 20 亿输入 token、生成了 1.4 亿输出 token，总花费不到 $20,000。就算和 Claude Max 最贵的套餐比，这也是个极其昂贵的项目。但和我要亲自做出这个东西的代价相比，这个总数只是一小部分——更别提一个整个团队了。

    这是一次 clean-room 实现（开发过程中 Claude 全程没有联网）；它只依赖 Rust 标准库。这个 100,000 行的编译器能在 x86、ARM 和 RISC-V 上构建可启动的 Linux 6.9。它还能编译 QEMU、FFmpeg、SQlite、postgres、redis，在大多数编译器测试集上都有 99% 的通过率，包括 GCC torture test suite。它也通过了开发者最终的试金石：能编译并运行 Doom。

    不过，这个编译器也有局限。包括：

  • 它缺少把 Linux 从 real mode 引导起来所需的 16 位 x86 编译器，这一步会转而调用 GCC（x86_32 和 x86_64 的编译器是它自己的）。
  • 它没有自己的汇编器和链接器；这两块是 Claude 最后才开始自动化的部分，而且还有不少 bug。演示视频是用 GCC 的汇编器和链接器做的。
  • 这个编译器能成功构建很多项目，但不是全部。它还无法直接顶替一个真正的编译器。
  • 生成的代码效率不高。就算打开全部优化，它输出的代码也比关闭全部优化的 GCC 低效。
  • Rust 代码质量尚可，但和资深 Rust 程序员能写出来的水平相去甚远。

    • 最终得到的编译器已经接近 Opus 能力的极限。我（很努力地）尝试修复上面几个局限，但没有完全成功。新功能和 bug 修复经常破坏现有功能。

    一个特别棘手的例子：Opus 没能实现进入 16 位 real mode 所需的 16 位 x86 代码生成器。编译器能通过 66/67 opcode 前缀输出正确的 16 位 x86 代码，但编译产物超过 60kb，远超 Linux 强制的 32k 代码上限。于是 Claude 在这里直接作弊，把这一阶段交给 GCC（只有 x86 是这样。ARM 或 RISC-V 上，Claude 的编译器可以完全独立编译。）

    编译器的源代码已经公开。下载下来，读读代码，在你喜欢的 C 项目上试试。我一直觉得，了解语言模型能做什么的最好方式，是把它们推到极限，然后观察它们从哪里开始失效。接下来几天，我会继续让 Claude 提交新改动，如果你想看 Claude 如何持续尝试解决这些局限，可以跟着关注。

    展望

    每一代语言模型都带来新的使用方式。早期模型在 IDE 里做 tab 补全很有用。没过多久，模型就能根据 docstring 补全函数体。Claude Code 的发布把 agent 带进了主流，开发者开始和 Claude 结对编程。但这些产品都基于同一个假设：用户定义一个任务，LLM 跑几秒或几分钟给出答案，然后用户再给后续输入。

    Agent 团队展示了自主实现整个复杂项目的可能性。这让我们这些工具使用者可以把目标定得更大胆。

    我们还在早期，完全自主的开发伴随着真实的风险。开发时如果有人在 Claude 旁边盯着，可以确保质量稳定、实时发现错误。对自主系统来说，很容易一看到测试通过就以为活儿干完了，但实际很少如此。我过去做渗透测试，利用大公司产品的漏洞，所以想到程序员会部署自己从未亲自验证过的软件，是一个实实在在令人担忧的问题。

    所以，这个实验让我兴奋，也让我感到不安。构建这个编译器是我最近觉得最有意思的事之一，但我没想到这件事在 2026 年这么早就已接近现实。语言模型和我们用来与它们交互的 scaffold 都在快速进步，这打开了一扇门：可以写出海量新代码。我预期正面应用会压过负面，但我们正在进入一个新世界，需要新的策略才能安全地前行。
