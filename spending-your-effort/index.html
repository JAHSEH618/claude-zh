使用 Claude Code：怎么花你的 effort

Sep 25, 2026Claude Code Blog约 8 minThariq Shihipar

effort 到底是什么、在 Claude Code 里什么时候用哪一档——来自我对三个构建的自测，以及在 Opus 5.5 和 Fable 5.1 上对 Terminal-Bench 3.0 的深挖。

目录

  1. What is effort?
  2. Effort curves
  3. Building with effort
  4. How effort levels impact output on difficult tasks

我们最新的 Claude 模型最棒的地方之一，是它们对 effort 的响应不会打破 Claude Code 里的 prompt cache，但我也收到用户很多关于这个的问题。effort 到底是什么，什么时候用哪一档？我们为什么需要 effort？

要回答这个，我决定深挖 evals，并自己对 effort 在日常工作里做测试。

总的来说，我发现 effort 是个调节 Claude 做多少验证和 edge case 测试、用多少自己判断的好办法。多花的 effort 在验证和 edge case 测试更有用的领域效果更好，比如硬件、code review、安全。

日常软件工程里，我在跑这样一个循环：让模型先采访我，low effort 实现，审一遍它构建的东西，再用 high effort 跑验证。

effort 是什么？

总的来说，effort 给模型一个近似值：你想让它在这个任务上花多少算力。它和你怎么估计任务难度有点关系。

可以这样想：有人让你连续做 12 小时一件事，你可能默认他们就是想要结果，会非常尽力。有人让你 1 小时做同一个任务，你会尽力给出一个满足要求的版本，然后预期在此基础上迭代。

或者你可能会顶回去，说这个任务至少要 3 小时，然后做 3 小时交付。

effort 应该这样理解。Claude 总会尽力把任务做到合理，但更高的 effort 意味着 Claude 做更多独立的判断和验证动作。

effort 曲线

Fable 5.1 和 Opus 5.5 的 effort 曲线是迄今最好的：每一档，benchmark 分数和消耗的 token 都往上跳一步。

Terminal-Bench 3.0

但实践中这意味着什么？为了评估，我在不同 effort 档试了几个任务，并仔细看了 benchmark。

用 effort 构建

理解模型怎么工作的最好办法是跑实验。我在 Opus 5.5 上用不同 effort 档做同样的任务，理解它会做什么活。我试了各种各样的活，这里用几个玩具例子说明。

欠规约的构建任务

如果我让 Claude "构建一个个人健身和工作量追踪 app"，effort 会极大地改变 app 的完整度，也会让 Claude 一路做更多选择。low effort 下，健身 app 就是一个日志加一个简单图表。更高的 effort 档，app 更复杂、细节更多。max effort 下有一张热力图。

如果我想一个简单的可以迭代的底子，low effort 就够了。max effort 是当我想要 Claude 一次做到最好。

轻规约的设计任务

如果任务已经比较规约清楚，但我想和 Claude 做一些探索呢？举例，我让它重新设计 Claude Code 的 /config 菜单。每一档做出来的想法大体一样：用子菜单和更好的搜索。

low effort（花 1 分钟），我拿到一个交互草图，传达了想法，但看起来不太像 Claude Code。

max effort（花 28 分钟），我拿到一个非常像 Claude Code 的 mockup，外加一批不同流程的 walkthrough。

如果我的目标是迭代和给反馈，low effort 会快得多到达那里。但 max effort 一开始就给我一个精细得多的东西。就这个任务而言，我更喜欢用 low effort 理解 Claude 的构想。

高规约的构建任务

如果我给 Claude 很多细节呢？我让它就健身 app 深度采访我，然后把那份 spec 交给不同模型在不同 effort 档实现。

我发现给了这份 spec，模型行为相似得多。我拿到外观比较像、实现相近但细节不同的设计，max effort 时 Claude 花时间简化了几个细节。

要点

常规软件工程，尤其新功能开发，effort 档很取决于我想多在环内。low effort 让 Claude 快速给出一个起点，更高的档会做更多活，但 Claude 也会替我做更多假设。

我在功能开发中一直在用的一个特别高产的循环：

  • 给 Claude 一份 spec，让它采访我补上我漏掉的细节
  • low effort 实现
  • 审一遍确认它抓住了大意，必要时 low effort 迭代
  • high effort 验证和测试

    • difficult 任务上 effort 档如何影响输出

    但这些显然是玩具例子，Claude 都能轻松完成。当差别在于 Claude 完成任务还是没完成任务时呢？

    要找这些难问题，得去 benchmark，所以我深挖了一个我喜欢的：Terminal-Bench 3.0，一个社区来源的 benchmark。

    Terminal-Bench 3.0 的问题大体可以分成安全、硬件、ML、科学、软件、运维、媒体等类别。所有问题在这里：https://github.com/harbor-framework/terminal-bench/releases/tag/v3.0.0。问题来自社区，任何人都可以贡献。

    值得读一遍，感受一下这些模型面对的问题类型。我发现很多任务的范围和野心让我惊讶。它们比我平常遇到的任务复杂得多。

    比如，其中一些任务包括：

  • 硬件（retro-console-soc）：用 Verilog 造一个能装进小型 FPGA 的 8 位游戏机，渲染一个测试 ROM。
  • 科学（takens-embedding-lean）：在 Lean 4 里形式化证明 Takens 嵌入定理。
  • ML（mp-checkpoint-consolidation）：把一个 mixture-of-experts checkpoint 的 16 个分片合并成一个能复现参考 logits 的文件。
  • 运维（intrastat-meldung）：端到端跑完一个公司月末的欧盟贸易统计申报。
  • 媒体（layout-config-recreation）：把一张海报图重建为可编辑的排版文件。

    • edge case 多的时候，更高的 effort 档有帮助

    读 Terminal-Bench 3.0 结果，我的主要收获是：hidden edge case 多的任务，更高的 effort 最好。

    一个干净的例子是 html-js-filter，一个要求写 HTML sanitizer、剥掉一切把 JavaScript 夹带进页面的方式的 Terminal-Bench 3.0 任务。Fable 5.1 从 low 的 1/5 到 xhigh 的 5/5。¹

    low effort 的典型尝试花约 2 分钟。每次尝试大体一遍写完 filter，然后对着一张手写页面测。

    high-effort 的运行约 33 分钟结束。在我追踪的那次运行里，它对抗性地审了自己的初稿，然后读安装的解析器源码查 bug，跑大量干净测试用例直到输出和输入一致，跑了一个标准 XSS 测试套件，最后写了一个随机文档 fuzzer。

    对 HTML sanitizer 这种 edge case 极多的东西，这些多花的 effort 很值。为彻底多花 token 对生产要求高的复杂任务（如性能优化、安全审查）也说得通。

    但每个任务都不需要这个级别的 effort。

    下面的图展示了所有 Terminal-Bench 3.0 结果和失败方式，跨不同模型和 effort 档。总体看，提高 effort 倾向减少因漏 edge case 的失败（紫色块），但模型思路错误时（蓝色块）它修不了。

    effort 有帮助的问题领域

    我在 Terminal-Bench 3.0 上评估这些模型，最有意思的收获之一：有些问题领域比别的从 effort 里受益更多。下图是细分：

    为说明这点，我从 Terminal-Bench 3.0 不同领域挑了几个 Opus 5.5 在 low effort 失败、high effort 成功的问题——大多因为它测试并处理了 edge case：

    mvcc-lsm-compaction：一个从崩溃报告修存储引擎 bug、且不能破坏 compaction 的 Terminal-Bench 3.0 任务。Opus 5.5 从 low 的 0/5 到 xhigh 的 4/5。

    low（每次尝试约一分钟），Claude 会先改代码再构建或跑复现程序，也没检查它的新测试能否抓住原始 bug。

    xhigh（约 11 分钟），Claude 先复现崩溃，对着一个从不 compact 的参考写随机化测试，并检查它的测试在半成品的修复上会失败。

    cli-2ph-simplex：一个要求用 Python 写 CLI 线性规划求解器的 Terminal-Bench 3.0 任务。Opus 5.5 从 low 的 0/5 到 high 的 5/5。

    low 的尝试一遍写完求解器，用几个小问题检查后就停在约 10k token 左右。最后一条消息里，Claude 警告它在大问题上可能慢，但没去验证。

    high 的尝试中，Claude 用随机问题把它的求解器和一个独立的暴力求解器对测，然后计时更大的问题，撞出运行过久或崩溃的情况，重做了它的搜索。

    gsea-proteomics：一个要求对蛋白质组学数据做基因集富集分析（GSEA）、找出八种处理里哪个最像目标组织的 Terminal-Bench 3.0 任务。Opus 5.5 从 low 的 0/5 到 high 的 4/5。

    low effort 下，Claude 挑了一个听起来合理的预处理方式，按那一种跑了分析，报告了结果。

    high 下，Claude 试了两种数据预处理方式，注意到显著处理的列表变了，深入查明原因后才选了正确的那个。

    如果用户在环内，Claude 也许会问用户问题该怎么设定，但没有用户在环内时，high effort 做得更好。

    在 Claude Code 里什么时候用哪个 effort 档

    我判断何时用哪一档的准绳：

  • Low：我想要在环内的快速响应时，比如头脑风暴、草图、简单改动
  • Medium：大多数常规软件工程，比如新功能实现。
  • High：验证重要或有 edge case 的活，比如修 brownfield 代码库里的 bug。
  • Max：想让 Claude 全自主运行去解决难题时，比如端到端构建并验证一个 app、在关键软件里找安全漏洞。

    • 试试在 Opus 5.5 和 Fable 5.1 上按任务变 effort，甚至在对话中途用 Claude Code 的 /effort 变，告诉我这是否符合你的直觉。

    ¹ 关于数字的说明：这些来自我们自己的内部运行，每任务 5 次尝试，Fable 5.1 关掉了我们的生产安全干预；在 Claude 产品里，Fable 5.1 的 safeguards 会把一些安全请求交给 Opus。安全任务也是无网络访问运行的，所以这里的每任务次数和公开 leaderboard 或发布文章对不上。具体例子来自单次运行，部分在中间 effort 设置上。
