Engineering at Anthropic

设计抗 AI 的技术评估

Published Jan 21, 2026Anthropic Research

一份性能工程 take-home 被 Claude 连续击败三版，我们学到了什么。

本文作者 Tristan Hume 是 Anthropic 性能优化团队的负责人。这份帮助 Anthropic 招到数十名性能工程师的 take-home 测试，由他设计——并且一次又一次地重新设计。

随着 AI 能力提升，评估技术候选人越来越难。今天能有效区分不同水平工程师的 take-home，明天可能就被模型轻松解开，彻底失去评估价值。

从 2024 年初开始，我们的性能工程团队一直在用一份 take-home 测试：要求候选人为一台模拟加速器优化代码。超过 1,000 名候选人完成了它，其中数十人已经在我们这里工作，包括把我们的 Trainium 集群从零拉起来的工程师，以及参与交付 Claude 3 Opus 之后每一个模型的工程师。

但每一代新的 Claude 模型都迫使我们重新设计测试。在同样的时间限制下，Claude Opus 4 的表现超过了大多数人类申请者。这还能让我们筛出最强的候选人——直到 Claude Opus 4.5 把这些人也追平了。给足时间，人类依然能超过模型，但在 take-home 的约束下，我们已经无法区分顶尖候选人的产出和我们最强模型的产出。

到目前为止，我已经把 take-home 迭代到第三版，只为确保它仍然有区分度。每一次迭代，我都学到一些关于"什么能让评估扛住 AI 辅助、什么不能"的新东西。

这篇文章介绍原始 take-home 的设计，每一代 Claude 模型是如何击败它的，以及我为了不让我们的最强模型刷爆测试、不得不采取的越来越出格的手段。我们的工作随着模型一起演变，但我们依然需要更多强工程师——只是找到他们的方式必须越来越有创意。

为此，我们把原始 take-home 作为公开挑战发布出来：在不限时的情况下，人类的最好成绩仍然超过 Claude 能达到的水平。如果你能胜过 Opus 4.5，希望听到你的消息——详情见文末。

take-home 的由来

2023 年 11 月，我们正在准备训练和发布 Claude Opus 3。当时我们已经锁定了新的 TPU 和 GPU 集群，大型 Trainium 集群也即将到来，在加速器上的开支远超以往，但性能工程师的数量撑不起新的规模。我在 Twitter 上发帖，请大家直接给我们发邮件。结果，有潜力的候选人远超我们标准面试流程能处理的数量，而那套流程对员工和候选人都要消耗大量时间

我们需要一种更高效的方式来评估候选人。于是我花了两周设计一份 take-home 测试，要能如实反映这个岗位的要求，并挑出能力最强的申请者。

设计目标

take-home 的名声一向不好：通常塞满了让工程师觉得无聊的通用题，过滤效果也差。我的目标不一样——做一份足够吸引人的题目，让候选人期待参与，让我们能高分辨率地看清他们的技术能力。

和现场面试相比，这个形式在考察性能工程能力上还有几项优势：

时间窗口更长：工程师写代码时几乎遇不到一小时以内的 deadline。4 小时（后来缩为 2 小时）更接近真实工作的节奏。它仍比大多数实际任务短，但这要和它给候选人带来的负担做平衡。

环境真实：没有人在旁边看着，也不要求边做边口述思路。候选人在自己的编辑器里无干扰地工作。

留足理解与造工具的时间：性能优化需要先理解现有系统，有时还要造调试工具。这两件事在常规的 50 分钟面试里都很难真实考察。

兼容 AI 辅助：Anthropic 的候选人通用指引要求候选人在没有特别说明的情况下不使用 AI 完成 take-home。而这份 take-home，我们明确标注了例外。

周期更长的题目更难被 AI 完整解决，候选人可以像工作中那样使用 AI 工具，同时仍要展示自己的能力。

除了这些形式本身的目标，我沿用在设计任何面试时用的同一套原则，让这份 take-home：

贴近真实工作：题目应该让候选人体验到这份工作实际包含什么。

高信号：take-home 要避开靠单一灵光一现就能解决的题，给候选人多次展示完整能力的机会，把运气成分压到最低。分数分布也要足够宽，深度也要够，让强候选人也做不完全部内容。

不要求特定领域知识：基本功扎实的人可以在工作中学细节。要求狭窄的专业背景会无谓地缩小候选人池。

好玩：快速的开发循环、有深度的问题、留出发挥创意的空间。

模拟机器

我用 Python 写了一个模拟器，模拟一台特性接近 TPU 的假加速器。候选人在这台机器上优化代码，配合一个支持热重载的 Perfetto trace，可以看到每一条指令，和我们 Trainium 上用的工具类似。

这台机器有几个让加速器优化变得有意思的特性：手动管理的 scratchpad 内存（和 CPU 不同，加速器通常需要显式的内存管理）、VLIW（每个周期多个执行单元并行运行，需要高效的指令打包）、SIMD（一条指令对多个元素做向量运算），以及多核（把工作分发到多个核上）。

题目是一道并行树遍历，刻意不带深度学习色彩：当时大多数性能工程师还没做过深度学习，领域细节可以入职再学。这道题的灵感来自 branchless SIMD 决策树推理，一个经典的 ML 优化问题，算是向过去致敬——此前只有少数候选人遇到过它。

候选人从一份完全串行的实现开始，逐步挖掘机器的并行能力。热身是多核并行，之后候选人自选：先做 SIMD 向量化还是 VLIW 指令打包。原始版本还藏了一个 bug，候选人需要先调试掉它，顺便考察了造工具的能力。


早期结果

第一版 take-home 效果很好。Twitter 那批人里有一位分数远超其他所有人。他 2 月初入职，比标准流程招到的第一批人只晚两周。这份测试被证明有预测力：他入职后立刻开始优化 kernel，还找到了一个阻塞发布的编译器 bug 的 workaround——张量索引运算溢出 32 位。

接下来的一年半里，约 1,000 名候选人完成了这份 take-home，现有性能工程团队的大部分成员都靠它招进来了。它对简历经验有限的候选人尤其有价值：我们几位表现最好的工程师直接来自本科，但他们在 take-home 上展现的能力足够我们放心录用。

反馈很好。不少候选人因为玩得太投入，做过了 4 小时上限。不限时提交里最强的几份包含了完整的优化迷你编译器，还有几个我完全没料到的巧妙优化。

Claude Opus 4 击败了它

到 2025 年 5 月，Claude 3.7 Sonnet 已经悄悄逼近一个临界点：超过 50% 的候选人，还不如把整道题完全交给 Claude Code。随后我用一个 Claude Opus 4 的预发布版本做了 take-home。在 4 小时限制内，它找到的解法比几乎所有人都更优化。

这不是我第一次有面试题被 Claude 模型击败。2023 年我专门设计过一道现场面试题，因为当时的题目都围绕常见任务，早期 Claude 模型对这些有大量知识，解起来毫不费力。我试图设计一道更考察解题能力、更少依赖知识量的题，同时仍以我在工作中解决过的一个真实（但冷门）问题为底。Claude 3 Opus 击败了我们那道题的第一部分，Claude 3.5 Sonnet 击败了第二部分。这道题我们至今还在用，因为我们其他的现场题同样不抗 AI。

take-home 有个直接的修法。这道题的深度远超任何人 4 小时能探索的范围，所以我让 Claude Opus 4 找出它开始吃力的位置，把那个位置设为第二版的起点。我重写了更干净的起步代码，加入新的机器特性增加深度，并删掉了多核——Claude 已经解决了多核部分，而它只会拖慢开发循环，不带来任何信号。

我还把时间限制从 4 小时缩到 2 小时。当初选 4 小时，是基于候选人的反馈：他们希望万一卡在某个 bug 或困惑上，被拖住的风险小一些。但排期开销在流程里造成了数周的延迟。2 小时则容易塞进一个周末。

第二版更看重巧妙的优化思路，弱化了调试和代码量。它很好地服务了我们——持续了几个月。

Claude Opus 4.5 又把它击败了

我测试一个 Claude Opus 4.5 的预发布 checkpoint 时，看着 Claude Code 在这道题上干了 2 小时，解法一步步变好。它解决了最初的瓶颈，实现了所有常见的微优化，不到一小时就达到我们的及格线。

然后它停了下来，认定自己撞上了一道无法逾越的内存带宽瓶颈。大多数人类也会得出同样的结论。但存在巧妙的技巧，利用问题结构绕开这个瓶颈。当我告诉 Claude 能达到的 cycle 数，它思考了一会儿，找到了技巧，接着调试、调优、继续叠加优化。到 2 小时整，它的分数追平了该时间限制内最好的人类成绩——而那个人类全程大量使用了带人工引导的 Claude 4。

为了更严格，我们在内部的 test-time compute harness 里跑了一遍，确认它既能 2 小时内击败人类，还能随时间继续涨分。发布之后，我们又对 harness 做了一次通用改进，刷出了更高分。

我遇到麻烦了。我们即将发布的模型，会让"把 take-home 交给 Claude Code"成为最优策略。


权衡备选方案

有同事建议禁止 AI 辅助。我不想这么做。除了执行上的困难，我有一个判断：既然人在我们的工作中继续扮演关键角色，我就应该能找出某种方式，让他们在有 AI 的环境——就像工作中那样——脱颖而出。我还不想现在就向这种观点让步：人类只在长于几小时的任务上才有优势。

也有人建议把标准抬到"大幅超过 Claude Code 单独能达到的水平"。顾虑在于 Claude 很快：人类通常要花掉 2 小时里的一半去读题和理解问题，才开始优化。一个人想引导 Claude，大概率全程落后，只能事后理解 Claude 做了什么。占优策略可能变成靠边坐着看。

如今 Anthropic 的性能工程师依然有大量工作要做，但内容更像高难度调试、系统设计、性能分析、想清楚如何验证系统正确性、以及如何把 Claude 写的代码改得更简单优雅。遗憾的是，要客观考察上述能力，要么花大量时间，要么需要共同上下文。设计出能代表这份工作的面试一直很难，现在比以往任何时候都难。

但我也担心：如果投入精力设计新的 take-home，要么 Claude Opus 4.5 把它也解掉，要么它难到人类两小时内根本做不完。

尝试 1：换一个优化问题

我意识到，无论我设计出什么，Claude 都能很快帮我落地，这反而促使我去做一份更难的 take-home。我选了一道题，基于我在 Anthropic 做过的一个较难的 kernel 优化：在 2D TPU 寄存器上高效做数据转置，同时避免bank conflict。我把它浓缩成模拟机器上更简单的题目，让 Claude 在一天内实现了全部改动。

Claude Opus 4.5 找到了一个我完全没想到的漂亮优化。它仔细分析后发现，可以整个计算一起转置，省去逐块转置数据的麻烦，并据此重写了整个程序。

在我的真实场景里这个方案行不通，所以我补了题目，把这个思路堵死。Claude 又取得了一些进展，但没找到最高效的解法。看起来我拿到新题了，接下来只需希望人类候选人能足够快解出来。但我心里有点不踏实，于是用 Claude Code 的 "ultrathink" 功能配上更长的思考预算复核了一遍……它解出来了，连修复 bank conflict 的技巧都知道。

回头看，这道题选错了。众多平台的工程师都和数据转置、bank conflict 较过劲，Claude 有足够多的训练数据可以调用。我是从第一性原理解出这道题的，Claude 则能调用更大的经验工具箱。

尝试 2：更怪的路子

我需要一道足够 out-of-distribution 的题，让人类推理能赢过 Claude 庞大的经验库。可惜这跟"让人认得出就是真实工作"的目标冲突。

我想了想自己享受过的最古怪的优化问题，最后落在 Zachtronics 的游戏上。这类编程解谜游戏使用怪异、约束极强的指令集，逼你用非常规的方式编程。比如 Shenzhen I/O 里，程序被拆到多颗互相通信的芯片上，每颗芯片只能容纳约 10 条指令，外加一两个状态寄存器。巧妙的优化常常是把状态编码进指令指针或分支标志。

我设计了一份新 take-home：一组谜题，用极小、约束极重的指令集编程，目标是最小化指令数。我先实现了一道中等难度的谜题，拿 Claude Opus 4.5 测试。它失败了。我补全了更多谜题，让同事验证：比我更不沉浸在这道题里的人，依然能胜过 Claude。

和 Zachtronics 的游戏不同，我刻意不提供任何可视化和调试工具。起步代码只检查解法是否合法。造调试工具本身就是考察的一部分：你可以精心插一组 print 语句，也可以让 coding model 花几分钟生成一个交互式 debugger。在工具投入上怎么做判断，本身就在信号里。

我对新 take-home 还算满意。因为独立子题更多，分数方差可能比原版低。早期结果不错：分数和候选人过往工作的水准相关性很好，我团队里最能打的同事之一，分数超过了此前所有候选人。

放弃原版的真实感和深浅不一的难度层次，我仍觉得可惜。但真实感可能已经是我们用不起的奢侈品。原版有效，是因为它像真实工作；替代品有效，是因为它模拟了新颖工作。


一个公开挑战

我们把原始 take-home 公开出来，任何人都不限时参与。时间尺度足够长时，人类专家对当前模型仍保有优势。有史以来提交的最快人类解法，大幅超过了 Claude 即使投入大量 test-time compute 的成绩。

公开版从零开始（同第一版），但用第二版的指令集和单核设计，所以 cycle 数能直接和第二版对比。

性能 benchmark（以模拟机器的时钟周期计）：

  • 2164 cycles：Claude Opus 4 在 test-time compute harness 里跑了数小时后
  • 1790 cycles：Claude Opus 4.5 在一次随意的 Claude Code 会话里，约等于人类 2 小时内的最好成绩
  • 1579 cycles：Claude Opus 4.5 在我们的 test-time compute harness 里跑 2 小时后
  • 1548 cycles：Claude Sonnet 4.5 投入远超 2 小时的 test-time compute 后
  • 1487 cycles：Claude Opus 4.5 在 harness 里跑 11.5 小时后
  • 1363 cycles：Claude Opus 4.5 在改进后的 test-time compute harness 里跑数小时后

    或者，走我们的常规流程申请，那套流程用的正是我们（现在）抗 Claude 的 take-home。我们很好奇它能撑多久。
