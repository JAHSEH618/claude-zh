用 MCP 做代码执行：构建更高效的 Agent

Published Nov 04, 2025Anthropic Research

直接的工具调用要为每个定义和结果消耗 context。更好的扩展方式，是让 Agent 写代码来调用工具。下面看看它在 MCP 里是怎么运作的。

Model Context Protocol（MCP） 是一个把 AI agent 连接到外部系统的开放标准。传统做法里，agent 每对接一个工具或数据源都要单独做一套集成，碎片化和重复劳动让真正打通的系统很难扩展。MCP 提供了一个通用协议——开发者在 agent 里实现一次 MCP，就能接入整个集成生态。

自 2024 年 11 月发布 MCP 以来，采用速度很快：社区已经构建了数千个 MCP server，SDK 覆盖了所有主流编程语言，业界也把 MCP 当作连接 agent 与工具、数据的事实标准。

如今开发者构建的 agent 通常能访问几十台 MCP server 上的数百乃至数千个工具。但连入的工具越多，把所有工具定义提前载入 context、再让中间结果穿过 context window，就会拖慢 agent、推高成本。

这篇博客会讲代码执行如何让 agent 更高效地与 MCP server 打交道——用更少的 token 处理更多工具。

工具消耗过多 token，拖累 agent 效率

MCP 用得多起来之后，有两种常见模式会拉高 agent 的成本和延迟：

  • 工具定义把 context window 塞满；
  • 工具调用的中间结果额外消耗 token。

    • 1. 工具定义撑爆 context window

    大多数 MCP client 会提前把所有工具定义直接装进 context，用直接工具调用的语法暴露给模型。这些工具定义大概长这样：

    工具描述占用的 context window 越多，响应时间和成本就越高。当 agent 连了上千个工具时，它读完一条请求之前，可能要先处理几十万 token。

    2. 中间结果额外消耗 token

    大多数 MCP client 允许模型直接调用 MCP 工具。比如你可以让 agent："把我在 Google Drive 里的会议记录下载下来，附到 Salesforce 的 lead 上。"

    面对大文档或复杂数据结构，模型在工具调用之间搬运数据时更容易出错。

    MCP 代码执行提升 context 效率

    代码执行环境在 agent 里越来越常见，一个解法是把 MCP server 暴露成代码 API，而不是直接工具调用。agent 随后写代码与 MCP server 交互。这种方式同时解决了上面两个问题：agent 只加载需要的工具，先在执行环境里处理数据，再把结果交回模型。

    Cloudflare 也发布了类似的发现，把 MCP 代码执行称为 "Code Mode"。核心洞见是一样的：LLM 擅长写代码，开发者应该利用这一点，构建与 MCP server 交互更高效的 agent。

    MCP 代码执行的好处

    MCP 代码执行让 agent 更高效地使用 context：按需加载工具、在数据到达模型之前先过滤、一步执行复杂逻辑。这种方式在安全和状态管理上也有好处。

    渐进式披露

    模型很擅长在文件系统里导航。把工具以代码形式放在文件系统上，模型就能按需读取工具定义，而不必一次性全部读完。

    另一种做法是给 server 加一个 search_tools 工具来检索相关定义。比如处理上面那个假设的 Salesforce server 时，agent 搜索 "salesforce"，只加载当前任务需要的工具。search_tools 里再加一个 detail level 参数，让 agent 选择需要的详细程度（比如只要名称、名称加描述、或带 schema 的完整定义），也能帮 agent 节省 context、更高效地找到工具。

    隐私保护

    agent 用 MCP 代码执行时，中间结果默认留在执行环境里。agent 只能看到你显式 log 或 return 的内容——你不想给模型看的数据，可以流经整个工作流而从不进入模型的 context。

    这和 Skills 的概念紧密相关——Skills 就是为模型准备的、存放可复用指令、脚本和资源的文件夹，用于提升模型在专门任务上的表现。给这些保存下来的函数加上一个 SKILL.md 文件，就形成了一个结构化的 skill，模型可以引用并使用。日积月累，agent 会积累起一套更高层能力的工具箱，不断演进出它高效工作所需的脚手架。

    注意，代码执行也带来自己的复杂度。运行 agent 生成的代码，需要一个安全的执行环境，配上适当的 sandboxing、资源限制和监控。这些基础设施要求增加了运维开销和安全考量，而直接工具调用可以避开这些。代码执行的好处——更低的 token 成本、更低的延迟、更好的工具组合——要和这些实现成本放在一起权衡。

    总结

    MCP 为 agent 连接大量工具和系统提供了基础协议。但连接太多 server 之后，工具定义和结果可能消耗过多 token，拖累 agent 效率。

    这里提到的很多问题——context 管理、工具组合、状态持久化——听起来很新，但软件工程早有成熟解法。代码执行把这些成熟模式应用到 agent 上，让它们用熟悉的编程结构更高效地与 MCP server 交互。如果你落地了这种方式，欢迎把你的发现分享给 MCP 社区。

    // ./servers/google-drive/getDocument.ts
import { callMCPTool } from "../../../client.js";

interface GetDocumentInput {
  documentId: string;
}

interface GetDocumentResponse {
  content: string;
}

/* Read a document from Google Drive */
export async function getDocument(input: GetDocumentInput): Promise<GetDocumentResponse> {
  return callMCPTool<GetDocumentResponse>('google_drive__get_document', input);
}

import * as gdrive from './servers/google-drive';
export async function saveSheetAsCsv(sheetId: string) {
  const data = await gdrive.getSheet({ sheetId });
  const csv = data.map(row => row.join(',')).join('\n');
  await fs.writeFile(`./workspace/sheet-${sheetId}.csv`, csv);
  return `./workspace/sheet-${sheetId}.csv`;
}
