像 agent 一样看：我们怎么在 Claude Code 里设计工具

Apr 10, 2026Claude Code Blog约 7 minThariq Shihipar

了解 Claude Code 团队怎么从模型的视角出发，设计、测试和演化工具。

目录

  1. Improving elicitation with the AskUserQuestion tool
  2. Designing a search interface

构建 agent harness 最难的部分之一，是构造它的工具。

Claude 完全通过 tool calling 行动，但在 Claude API 里构造工具有很多方式，可以用 bash、skills 和 code execution 这样的原语。（你可以在 @RLanceMartin 的新文章里读更多关于 Claude API 上 programmatic tool calling 的内容）。

那么你怎么设计 agent 的工具？给它一个像 bash 或 code execution 这样的通用工具？还是五十个专用工具，每个用例一个？

把自己放进模型的处境里，想象你被给了一道难题。为了解它，你想要什么工具？这取决于你自己的技能！

纸是最小的配置，但你会被手算限制住。计算器更好，但你需要会操作更高级的选项。最快最强的是一个电脑，但你得知道怎么用写代码和执行。

这是设计 agent 的一个有用框架。你想给它的工具要为它自己的能力塑形。但你怎么知道那些能力是什么？你留心、读它的输出、做实验。你学会像 agent 一样看。

如果你在构建 agent，你会面对和我们一样的问题：什么时候加工具、什么时候删一个、怎么区分。下面是我们在构建 Claude Code 时怎么回答这些的，包括我们一开始做错的地方。

用 AskUserQuestion 工具改进 elicitation

构建 AskUserQuestion 工具时，我们的目标是改进 Claude 提问的能力（常被称为 elicitation）。

Claude 本来就能用纯文本提问，但我们发现回答那些问题感觉花了不必要的时间。我们怎么降低这个摩擦、增加用户和 Claude 之间沟通的带宽？

尝试 1：改 ExitPlanTool

我们试的第一个方案是给 ExitPlanTool 加一个参数，让 plan 旁边带一组问题。这是最容易实现的修复，但它让 Claude 困惑，因为我们同时要一个 plan 和一组关于 plan 的问题。如果用户的回答和 plan 说的一致怎么办？Claude 需要调用两次 ExitPlanTool 吗？我们知道这个 tactic 行不通，于是回到画图板。（你可以读我们为什么做了一个 ExitPlanTool，见我们关于 prompt caching 的 post）

尝试 2：改输出格式

接下来，我们试了更新 Claude 的输出指令，让它用一个稍微改过的 markdown 格式来提问。比如，我们可以让它输出一组 bullet point 问题，选项放在方括号里。然后我们解析并把它格式化成给用户的 UI。

Claude 通常能产出这个格式，但不可靠。它会多贴句子、丢选项，或干脆放弃这个结构。下一个方案。

尝试 3：AskUserQuestion 工具

最后，我们落地到创建一个 Claude 可以任何时候调用的工具，但我们在 plan mode 里特别 prompt 它这么做。当工具触发，我们显示一个 modal 展示问题，并阻塞 agent 的循环直到用户回答。

这个工具让我们能 prompt Claude 产出结构化输出，也帮我们确保 Claude 给用户多个选项。它还给了用户组合这个功能的方式，比如在 Agent SDK 里调用它，或在 skills 里引用它。

最重要的是，Claude 似乎很喜欢调用这个工具，我们发现它的输出效果好。毕竟，即使设计得最好的工具，如果 Claude 不懂怎么调用也白搭。

这是 Claude Code 里 elicitation 的最终形态吗？我们怀疑。随着 Claude 变强，服务它的工具也得演化。下一节讲一个工具从帮忙变成碍事的例子。

随能力更新：tasks & todos

我们刚发布 Claude Code 时，意识到模型需要一个 todo list 来保持正轨。Todos 可以在开始时写下来，随着模型干活逐项勾掉。为此我们给了 Claude 一个 TodoWrite 工具，用来写或更新 Todos 并展示给用户。

但即便如此，我们经常看到 Claude 忘记它要做什么。为了适应，我们每 5 个 turn 插入一次 system reminder，提醒 Claude 它的目标。

随着模型变好，它们发现 To-do list 限制了它们。被反复提醒 todo list 让 Claude 觉得必须照清单执行，而不是在它意识到需要改方向时修改它。我们还看到 Opus 4.5 在用 subagents 上好了很多，但 subagents 怎么在共享的 todo list 上协调？

看到这点，我们用 Task 工具 替代了 TodoWrite 功能。Todos 专注于让模型保持正轨，tasks 则帮 agent 互相沟通。Tasks 可以包含依赖、跨 subagents 共享更新，模型也可以改和删它们。

随着模型能力提升，你的模型曾经需要的工具现在可能在限制它们。不断重访"需要哪些工具"的旧假设很重要。这也是为什么坚持支持一小批能力画像相当相似的模型很有用。

设计一个搜索接口

我们构建的最有分量的工具，是那些让 Claude 找到自己 context 的工具。

Claude Code 刚内部发布时，我们用 RAG：一个向量数据库预索引代码库，harness 在每次回复前检索相关片段交给 Claude。RAG 强也快，但它需要索引和 setup，在一堆不同环境里可能脆弱。最重要的是，Claude 是被给这个 context，而不是自己找 context。

但如果 Claude 能搜网页，为什么不能也搜你的代码库？通过给 Claude 一个 Grep 工具，我们能让它自己搜文件、自己构建 context。

随着 Claude 变聪明，给它对的工具时它构建自己 context 的能力越来越强。

当我们引入 Agent Skills 时，我们把 progressive disclosure 这个想法正式化了，它让 agent 通过探索逐步发现相关 context。

Claude 现在能读 skill 文件，那些文件又能引用其他模型可以递归读的文件。事实上，skills 的一个常见用法是给 Claude 加更多搜索能力，比如告诉它怎么用一个 API 或查一个数据库。

一年下来，Claude 从基本不能构建自己的 context，变成能在跨好几层文件的嵌套搜索里找到它需要的精确 context。

Progressive disclosure 现在是我们用来加新功能而不加工具的常用技术。下一节解释为什么。

Progressive disclosure：Claude Code Guide agent

Claude Code 目前有约 20 个工具，我们的团队经常重访是否都需要它们才能让 Claude 最有效。加新工具的门槛很高，因为这给了模型多一个要想的选项。

比如，我们注意到 Claude 对怎么用 Claude Code 了解得不够。你问它怎么加一个 MCP 或一个 slash command 是什么，它答不上来。

我们可以把所有这些信息放进 system prompt，但鉴于用户很少问这个，那会加入 context rot 并干扰 Claude Code 的主业：写代码。

反过来，我们试了 progressive disclosure：给 Claude 一个指向它文档的链接，需要时可以加载和搜索。这奏效了，但 Claude 会拉大段文档进 context，去回答一个用户一句话就能得到的答案。

所以我们构建了 Claude Code Guide——一个 Claude 每次用户问 Claude Code 本身时调用的 subagent。Subagent 在它自己的 context 里做文档搜索，遵循详细的怎么搜、抽什么的指令，只把答案交回来。主 agent 的 context 保持干净。

虽然这不是完美方案（你问它怎么设置它自己时 Claude 还是可能困惑），但我们能在不加新工具的情况下往 Claude 的行动空间里加东西。

像 agent 一样看是一门艺术，不是一门科学

为你的模型设计工具，和科学一样是一门艺术。它很大程度上取决于你用的模型、agent 的目标、以及它运行的环境。

我们最好的建议？多实验、读你的输出、试新东西。最重要的是，试着像 agent 一样看。

今天就用 Claude Code 开始。
