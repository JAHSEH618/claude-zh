让 Claude 能验证自己的工作

给 Claude 一个它能自己跑的检查：测试、构建、一张能对比的截图。这决定了你是必须盯着 session，还是可以走开不管。
策略 之前 之后 给出验证标准 ”实现一个校验邮箱地址的函数" "写一个 validateEmail 函数。测试用例示例：user@example.com 应为 true，无效输入为 false，user@.com 为 false。实现完成后跑一遍测试” 用视觉方式验证 UI 改动 ”让 dashboard 界面更好看" "[粘贴截图] 实现这个设计。对结果截图，和原图对比，列出差异并修复” 处理根因，而非表象 ”构建失败了" "构建报了这个错误：[粘贴错误信息].。修复它，并确认构建成功。解决根因，不要掩盖错误”
  • 一条 prompt 内：让 Claude 在同一条消息里执行检查并迭代，就像上面的表格那样。
  • 贯穿整个 session：把检查设为 /goal 条件。一个独立的 evaluator 会在每轮结束后复查，Claude 会持续工作直到 goal 达成。如果 Claude 卡住，Claude Code 最终会在 goal 仍处设置状态时停止本次运行——参见 /goal 的评估机制。
  • 作为确定性关卡：Stop hook 把你的检查当脚本运行，在通过之前阻止这一轮结束。Stop input 讲了连续拦截的上限。
  • 借助第二意见：验证 subagent 或会检查自身发现的 动态 workflow，会让一个全新的模型尝试推翻当前结果，干活的 Agent 不给自己打分。

    管理你的 session

    ​
    尽早、频繁地纠偏

    一发现 Claude 跑偏，立刻纠正。
  • Esc：Claude 执行到一半时，按 Esc 键让它停下。上下文保留着，你可以马上改方向。
  • Esc + Esc 或 /rewind：连按两次 Esc 或运行 /rewind，打开回退菜单，恢复之前的对话和代码状态，或者从选定的消息开始总结。
  • "Undo that"：让 Claude 撤销它的改动。
  • /clear：在不相关的任务之间重置上下文。带着无关上下文的长 session 会让表现变差。

    • ​
    主动管理上下文

    在不相关的任务之间运行 /clear，重置上下文。
  • 任务之间勤用 /clear，把 context window 整个重置
  • 自动压缩触发时，Claude 会总结最重要的内容，包括代码模式、文件状态和关键决策
  • 想要更多控制，运行 /compact <instructions>，比如 /compact Focus on the API changes
  • 只想压缩对话的一部分时，用 Esc + Esc 或 /rewind 选一个消息 checkpoint，再选 从这条消息开始总结 或 总结到这条消息。前者压缩该点之后的消息，保留之前的上下文；后者压缩较早的消息，保留最近消息的完整内容。参见 回退菜单里的总结选项。
  • 在 CLAUDE.md 里定制压缩行为，写上类似 "When compacting, always preserve the full list of modified files and any test commands" 的指令，确保关键上下文在总结后依然存在
  • 不需要留在 context 里的问题，用 /btw。回答不会进入对话历史，你可以查个细节而不让 context 变大。

    用 subagent 做调查

    用 "use subagents to investigate X" 这类 prompt 把调研委派出去。subagent 在单独的 context 里探索，主对话保持干净，专心做实现。

    用 checkpoint 回退

    每发出一条开启新回合的 prompt，都会创建一个 checkpoint。你可以把对话、代码或两者一起恢复到任意一个先前的 checkpoint。
    checkpoint 只跟踪 Claude 文件编辑工具产生的修改，Bash 命令或外部进程产生的修改不会被记录。checkpoint 不是 git 的替代品。

    ​
    恢复对话

    用 /rename 给 session 命名，像对待 branch 一样对待它们：每条工作流都有自己的持久 context。

    运行非交互模式

    在 CI、pre-commit hook 或脚本里用 claude -p "prompt"。加上 --output-format stream-json --verbose 可以获得流式 JSON 输出。

    并行运行多个 Claude session

    并行运行多个 Claude session：加快开发速度、做隔离实验，或者跑复杂的工作流。
  • Worktrees：在隔离的 git checkout 里各自跑 CLI session，编辑互不冲突
  • Cross-session messaging：让你自己启动的多个 session 互相传递调研结果
  • Desktop app：可视化管理多个本地 session，也可以让每个 session 放在自己的 worktree 里
  • 在云端使用 Claude Code：session 默认跑在 Anthropic 托管的基础设施上
  • Agent view：研究预览。运行 claude agents 派发在后台持续运行的 session，一块屏幕统一观察
  • Agent teams：实验性功能，默认关闭。多个 session 自动协调，共享任务、消息和一个 team lead
    • Session A（写代码） Session B（评审） Implement a rate limiter for our API endpoints Review the rate limiter implementation in @src/middleware/rateLimiter.ts. Look for edge cases, race conditions, and consistency with our existing middleware patterns. Here's the review feedback: [Session B output]. Address these issues.

    增加对抗式评审步骤

    在把任务标记为完成之前，让一个 subagent 在全新的 context 里评审 diff，并汇报缺口。
    被要求找问题的评审者，即使工作本身没问题，通常也会报出一些问题，因为这就是它的任务。追着每条发现去修，会导致过度设计：多余的抽象层、防御性代码、针对不可能发生场景的测试。告诉评审者只标记影响正确性或既定需求的缺口，其余的当作可选项。

    避免常见的失败模式

  • 大杂烩 session。你从一个任务开始，接着问 Claude 一个不相关的问题，又跳回第一个任务。Context 里塞满了无关信息。
    修法：用 /clear 隔开互不相关的任务。
  • 反复纠正。Claude 做错了，你纠正它，还是错的，你再纠正。Context 被各种失败的尝试污染。
    修法：纠正两次还没对，就 /clear，写一个更好的初始 prompt，把学到的写进去。
  • 写得太长的 CLAUDE.md。CLAUDE.md 太长的话，重要规则淹没在噪音里，Claude 会忽略其中一半。
    修法：狠心精简。Claude 不用指令就能做对的事，删掉这条说明，或者改成 hook。
  • 只信任、不验证。Claude 交出一套看起来合理的实现，却没处理边界情况。
    修法：始终提供验证手段（测试、脚本、截图）。无法验证的，就别上线。
  • 无界探索。你让 Claude “调查”某件事，却不给范围。Claude 读了几百个文件，把 context 塞满。
    修法：把调查范围收窄，或者用 subagent，别让探索吃掉主 context。

里已回答过的问题，说明措辞有歧义。把 CLAUDE.md 当代码对待：出问题时审查它、定期精简、观察 Claude 的行为是否真的改变来验证每次修改。对于已提交进仓库的 CLAUDE.md，跑 /doctor，Claude 会建议删掉那些它能从代码库自己推导出来的内容。 Claude 反复漏掉某一条指令时，只在那一行加上 “IMPORTANT” 这样的强调。强调太多行，就没有哪行突出了。把 CLAUDE.md 提交进 git，让团队一起维护。这个文件会随时间积累价值。 CLAUDE.md 可以用 @path/to/import 语法导入其他文件。导入规则和 CLAUDE.md 可以放在哪些位置，见 CLAUDE.md files。 Claude Code v2.1.283 起，交互终端和 VS Code session 的 内置起始权限模式是 auto mode：由一个独立的分类模型替你审查大部分操作，只拦截看起来有风险的动作，比如权限升级、未知基础设施、被恶意内容诱导的操作。更早的版本里，auto mode 只在 Pro、Max、Team 套餐中是内置起始权限模式。 Manual 模式下，Claude Code 在执行可能修改系统的动作前会先询问：写文件、Bash 命令、MCP 工具。这安全，但繁琐。点了十次批准之后，你是在机械点按钮，不是在审查。两个工具能减少 Manual 模式下的这些打断，在 auto mode 里同样生效： 更多资料见 权限模式、权限规则 和 沙箱。 CLI 工具是与外部服务交互最省 context 的方式。用 GitHub 的话，装上 gh CLI。Claude 知道用它建 issue、开 pull request、读评论。没有 gh，Claude 也能调 GitHub API，但未认证请求经常撞上 rate limit。 让 Claude 现学它不认识的 CLI 工具也很有效。试试这样的 prompt：Use 'foo-cli-tool --help' to learn about foo tool, then use it to solve A, B, C. 通过 MCP server，你可以让 Claude 按 issue tracker 里的需求实现功能、查数据库、分析监控数据、集成 Figma 设计稿、自动化工作流。 Hooks 在 Claude 工作流的特定节点自动运行脚本。CLAUDE.md 里的指令是建议性的，hook 则是确定性的，保证动作一定执行。 Claude 能替你写 hook。试试这样的 prompt：“Write a hook that runs eslint after every file edit” 或 “Write a hook that blocks writes to the migrations folder.” 手动配置 hook 直接编辑 .claude/settings.json，跑 /hooks 查看当前配置。 Skills 用你项目、团队或领域特有的信息扩展 Claude 的知识。相关时 Claude 会自动应用，你也可以用 /skill-name 直接调用。 在 .claude/skills/ 下加一个包含 SKILL.md 的目录，就创建了一个 skill： .claude/skills/api-conventions/SKILL.md Skill 也可以定义可重复调用的工作流： .claude/skills/fix-issue/SKILL.md 跑 /fix-issue 1234 调用它。有副作用、想手动触发的工作流，加 disable-model-invocation: true。 Subagent 在自己的 context 里运行，有自己的一套允许工具。需要读大量文件或专注处理、又不想弄脏主对话的任务，适合交给它们。 .claude/agents/security-reviewer.md 明确要求 Claude 使用 subagent：“Use a subagent to review this code for security issues.” Plugins 把 skills、hooks、subagent 和 MCP server 打包成一个可安装单元，来自社区和 Anthropic。用静态类型语言的话，装一个 code intelligence plugin，让 Claude 获得精确的符号导航，并在编辑后自动发现错误。 skills、subagent、hook 和 MCP 怎么选，见 扩展 Claude Code。 问 Claude 你会问另一位工程师的问题；功能大一点时，先让 Claude 访谈你、写好 spec，再开始实现。 熟悉一个新代码库时，用 Claude Code 学习和探索。你可以问 Claude 那些会问另一位工程师的问题： 这样用 Claude Code 是一个有效的 onboarding 流程：加快上手速度，也减轻其他工程师的负担。不需要什么特别的 prompt，直接提问就行。 Claude 会问你可能还没考虑过的问题，包括技术实现、UI/UX、边界情况和权衡。发送前把 [brief description] 替换成你的功能描述。 spec 写完后，开一个新 session 来执行。新 session 的 context 是干净的，完全聚焦实现，而你手里有一份可以对照的书面 spec。 最有用的 spec 是自包含的：写清楚涉及哪些文件和接口、哪些不在范围内，最后给一个端到端验证步骤，证明功能可用。花在把 spec 写精确上的时间，比盯着实现过程的回报更高。 对话是持久且可回退的。利用好这一点！ 最好的结果来自紧密的反馈循环。Claude 偶尔能一次就把问题解得完美，但快速纠正通常能更快得到更好的方案。 同一个问题在一个 session 里纠正 Claude 超过两次，context 里已经堆满失败的尝试。跑 /clear，用吸收了教训的、更具体的 prompt 重新开始。干净的 session 加上更好的 prompt，几乎总是赢过积累了层层纠正的长 session。 接近 context 上限时，Claude Code 会自动压缩对话历史，保留重要的代码和决定，腾出空间。 长 session 里，Claude 的 context window 会被无关的对话、文件内容和命令塞满。这会拉低性能，有时还会分散 Claude 的注意力。 context 是根本约束，用 subagent 把调研挡在外面。Claude 调研代码库时要读大量文件，这些文件全都会消耗你的 context。Subagent 在独立的 context window 里运行，回报摘要： Claude 实现完东西之后，也可以让 subagent 做验证。见 增加对抗式评审步骤。 Claude 在每次修改前自动给文件打快照，checkpoint 可以恢复它们。双击 Escape 或跑 /rewind 打开回退菜单。可以只恢复对话、只恢复代码、两者都恢复，也可以从某条消息开始总结。详情见 Checkpointing。 不必每一步都精心规划，可以让 Claude 去试有风险的路子。行不通就回退，换一种做法。Checkpoint 随对话保存，关掉终端、之后恢复 session，照样能回退。 Claude Code 把对话保存在本地，任务分几次做的话，不用重新解释 context。跑 claude --continue 接着上次的进度，或用 claude --resume 从列表里选。给 session 起有描述性的名字，比如 oauth-migration，方便之后找。恢复、分支、命名的完整控制项见 管理 session。 单个 Claude 用熟了，就用并行 session、非交互模式和扇出模式放大产出。 claude -p "your prompt" 可以非交互地运行 Claude，没有交互提示符。除非传 --no-session-persistence，否则这次运行仍会创建可恢复的 session。非交互模式就是把 Claude 接进 CI 流水线、pre-commit hook 或任何自动化工作流的方式。输出格式支持程序化解析结果：纯文本、JSON 或流式 JSON。 第一条命令输出纯文本。json 格式返回单个 JSON 对象，带 result 字段。stream-json 格式每行输出一个 JSON 对象，第一条是 init 事件。 选一个跟你想自己承担的协调量匹配的并行方式；session 之间需要传递发现时，加上 messaging： 多 session 除了能并行干活，还能支撑以质量为中心的工作流。全新 context 提升代码评审质量，因为 Claude 不会偏袒自己刚写的代码。 例如使用 Writer/Reviewer 模式： 测试可以照搬这个套路：一个 Claude 写测试，另一个 Claude 写代码去通过它们。 大型迁移或分析，可以把工作分发到大量并行的 Claude 调用上。跑 /batch <instruction>，Claude 会把改动拆给 5 到 30 个 subagent，每个 subagent 在自己的 worktree 里干活。想用自己的脚本驱动扇出，就循环调用 claude -p： 先让 Claude 把需要迁移的文件列表写进文件，供下一步的循环读取，prompt 类似 list all 2,000 Python files that need migrating and save the list to files.txt 根据前 2-3 个文件暴露的问题完善 prompt，再跑全量。--allowedTools 预先批准迁移需要的工具，--permission-mode dontAsk 会拒绝其余所有需要批准的动作——无人值守时这一点很关键。 Claude 也能接进现有的数据/处理流水线： 想要不中断执行、后台仍有安全检查，用 auto mode。分类模型在命令执行前审查，拦截权限升级、未知基础设施和被恶意内容诱导的操作，常规工作则无需提示直接放行。 带 -p 的非交互运行中，分类模型反复拦截动作时，Claude Code 不会终止运行。回退时发生什么、阈值是多少，见 auto mode 何时回退。 Claude 无人值守的时间越长，把活算作完成之前，独立检查就越重要。跑在全新 subagent context 里的评审者只看 diff 和你给的评判标准，看不到产生改动的推理过程，于是按自己的标准评估结果。 做正确性检查，跑内置的 /code-review skill：它在全新 subagent 里审查当前 diff 的 bug，并把发现带回 session。想按你的计划来审查 diff，就自己写评审 prompt：点明要审的工作、对照的计划、什么才算 finding： 评审者以 subagent 身份运行，实现 session 直接收到缺口清单，修完再复审，不用你在窗口之间复制发现。 常见错误如下，早点认出来能省时间： 这份指南里的模式不是刻板的。它们是普遍好用的起点，但不一定在每个场景下都最优。 有时你应该放任 context 积累——你正深陷一个复杂问题，历史很有价值。有时该跳过规划，让 Claude 自己琢磨——任务是探索性的。有时模糊的 prompt 恰好合适——你想先看看 Claude 怎么理解这个问题，再施加约束。 留意什么管用。Claude 交出好结果时，回想你做了什么：prompt 的结构、提供的 context、所处的 mode。Claude 卡壳时，问为什么：context 太吵？prompt 太模糊？任务太大，一次干不完？ 用久了，你会练出任何指南都概括不了的直觉。你会知道何时该具体、何时该开放，何时该规划、何时该探索，何时清 context、何时让它积累。
