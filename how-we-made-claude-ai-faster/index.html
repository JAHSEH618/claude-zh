我们如何在两周里让 claude.ai 快 3 倍

Sep 23, 2026Claude Code Blog约 15 minRaymond Wang, Sam Attard, and Issac G.

一旦 Claude 能测量一个东西，它就能把它变快。所以我们不断找更多能测的东西。

今年八月，我们在一个两周冲刺里，把 claude.ai 和 Claude 桌面应用的核心用户体验提速了约 3 倍。用户一直在跟我们说它慢，他们说得对。我们从单个 Slack channel 里推进一切，每个 thread 里都有 Claude。

我们聚焦占用户活动 95% 的四条 journey。第 75 百分位上，claude.ai 冷加载到可输入页面从 3.1 秒降到 0.55，启动新的 Claude Code session 从 0.8 秒降到 0.3，加载 Claude Cowork 云端 session 从 2.6 秒降到 0.73。合计估计每天省下数万个用户小时的等待。

核心用户 journey，p75

我们用了 Claude Tag（beta），跑一个内部研究模型，大致相当于 Opus 5.5。Claude 找瓶颈、建 benchmark、发改进、盯每次部署。我们通过定目标、做取舍、审批每个变更来掌舵。用那套做法，我们合了三千多个变更，没有一次面向客户的事故或回滚。这篇讲我们发了什么、怎么测量的、以及我们和 Claude 一起搭起来安全完成这一切的 loop。

任务简报

冲刺开始前，我们建了一个 Slack channel，放了下面的standing instructions：

@Claude 你的工作是推动 claude.ai 网站和桌面应用性能相关的一切。你的职责包括：监控部署里的性能回退，评估现有遥测的准确性和完整性，维护整理得当的可观测性 dashboard，主动为观察到的问题和低垂果实实现解决方案，提出性能项目机会，以及和你的人类队友沟通。[…]

这个 channel 的最终目标是让你尽可能自主，但今天我们都知道那还做不到。

我们让 Claude 通过 Datadog MCP server 分析用量数据。它识别出影响最大的四条用户 journey：启动应用、开始对话、加载已有对话、发送消息。跨 web 和桌面、跨我们的产品，这些 journey 对应十三项不同的测量。为了建立基线，我们加埋点直到它们可以直接比较：每项都从用户交互开始，到结果渲染完结束，并分清客户端和服务端的工作。

我们用一份约二十个手工挑选的项目清单启动冲刺，每个项目瞄准一条具体 journey。Claude 以毫秒估算每个项目的收益，我们汇总这些估算定下冲刺目标。有些项目相当大，但我们认为两周内大概能做完其中大部分。

第三天，我们击中了十三项目标里的十二项。

计划内项目提前落地。更快启动上，我们把一个静态 composer 烘焙进 HTML，让 React 初始化期间用户就能打字，并预编译了 V8 代码缓存，让桌面壳的主进程不必从头重编译。更快导航上，我们在对话之间保持 composer 挂载，用户悬停到 session 上时预取，并把侧边栏重渲染砍掉 90%。

我们还留了空间给 Claude 识别机会、提出新工作流。那些工作流很快长成完整的项目，远超我们最初的目标。于是我们定新目标，然后找更多能测的东西：

@Claude 我们已经资助了原始 projects 清单上几乎所有的项目，还有更多。来做一次 refresh […] 我们还没探索过什么，什么能 hill climb，现在最大的机会在哪里？[…] 我对 WACKY 想法持开放态度

任何东西都能被 hill climb

一开始我们就知道要比部署节奏迭代更快。Claude 能异步工作很多小时，甚至过夜，我们想让它不用等线上读数就能验证原型。为此，我们找实验室里测量性能的其他办法。

    我们对每个新 benchmark 都带着点怀疑。每个都有两个职责：第一，Claude 能在实验室里推动的指标；第二，CI 里一道只能棘轮往下调的护栏数字。benchmark 不稳定，或者跟用户延迟实际不相关，我们就扔掉，不让 Claude 爬错山。

    @Claude 请证明 hill climbing 这些每一项都能带来可测量的 wall clock 性能收益。证明不了的候选，我们把 bench 下线

    Wall-clock 时间是用户感受到的，但它有噪音，毫秒级太不稳，不能当 CI 门禁。指令数吸引人的地方在于确定性，但我们仍需 Claude 证明它跟 wall-clock 时间同步。

    所以我们让 Claude 把两条热路径的计数降下来：组装对话消息树的那个例程，和扫描 Claude Code 输出里状态行的 scanner。Claude 用 Valgrind 对两者做了 profile，发现第一条路径四分之一的指令是 megamorphic 字典查找，同一个 message ID 被单独解析了三次。

    一小时后，它把两条路径的指令砍了 48% 和 31%，wall-clock 时间降了 78% 和 44%。我们检查进两道新棘轮。从那以后，任何抬高那些路径指令数的 PR 都过不了 CI，一个每日 job 在计数下降时把每个上限调低。

    计数跟时钟同步吗？

    这把我们带到冲刺的核心理课。有了 Claude，能测量一个东西，它就可解。

    测量过去是第零步：加个指标，等数据进来，然后才开始理解问题。有了 Claude，它是攀登的第一步。Claude 一有可以打败的数字，就能开始优化。这意味着我们能做的杠杆最高的事，是找更多能测的东西。

    这个 loop，一个 thread 一个 thread 看

    这一切都在同一个 Slack channel 里跑，多个工程师和 Claude 在每个 thread 里 jam。从那之后，冲刺落进一个 loop：

  • 有人开一个 thread，讲某条 journey 里慢的段落，常带截图或录屏。
  • Claude 追踪那个流程，然后找到或造一个证明该问题的 benchmark。
  • 实验室里有 promising 结果后，Claude 带着 PR 回来——常常是几个，按风险和评审大小切分，用户可见的东西都放在 flag 后面。
  • 发出后，Claude 盯部署、读线上数据。
  • 性能变好，Claude 把 benchmark 棘轮下调，锁定收益；没变好，它把 flag 关掉再迭代。
  • 然后它去找同一条 journey 里下一个慢点。
    • loop 里的一个 thread

    例子：有人分享了一个录屏，显示侧边栏行在页面加载后才弹出。Chat 和 Cowork 的行在不同时间解析出来，页面感觉一顿一顿。我们现有的监控没有一个抓到它。最接近的是 Cumulative Layout Shift，但每次 shift 只算约 0.008 分——远在 0.1 的好阈值之内。

    Issac 想到直接引用底层的 Layout Instability API。Claude 造了一个遥测事件，把每个 layout-shift 条目的 sources 映射到命名区域（如 sidebar、transcript）和阶段（如 first paint 之前、可输入之后）。它加了一个集成测试，打开一个侧边栏已有内容的页面，把侧边栏数据扣到 first paint 之后才放，任何命名区域内出现 shift 就失败。Claude 拿它当 benchmark 证明修复：测试在 main 上 20 次运行 20 次红，在 PR 上 20 次 20 次绿。

    事件上线后，Claude 读线上数据，发现 31% 的 web 页面加载在页面可用之后还动了东西，没有任何用户交互。从那之后，Claude 点名逐个处理原因：晚到的表头行、用户名加载出来后横着滑位的 caret、滚动条弹出时移动列表。Claude 把最大的几个 offender 成批修掉，它们消失后，又找到下一批。

    那是一个 thread。冲刺期间，我们同时跑过一百五十多个。

    水平扩展

    loop 在一个 thread 上跑通后，在更多 thread 上跑只是开 thread 的事。原始请求满足后不关掉 thread，Claude 会继续做下去。单个 thread 会提五十个、有时一百个优化 PR。越来越多的是 Claude 而不是我们开新 thread，去追它自己发现的机会——来自另一次调查或夜间 job。Shelley，channel 里的一位工程师，观察到："[这个模型]是个 numbers demon。"

    每个测量都找到能改进的东西。Claude 做了 React hook 普查，在 composer 的打字路径上找到 6,900 个 hook 和 900 个 store 订阅，每次按键都在重渲染。Claude 数了样式重算，发现一个 :root:has() 选择器给每次 DOM 变更加 24 毫秒。Claude 追踪 first paint 之后的代码路径，发现一个残留的 location.reload()，每天造成五十万次我们任何加载指标都看不到的隐藏重载。Claude 读空闲标签页的 profiler 采样，发现相同的缓存快照每分钟被克隆进 IndexedDB 两次，全在主线程。

    我们很少知道一个 thread 会走到哪。一次扫 CPU 卡顿，Claude 注意到高亮一个写好的代码块能让页面冻住约一秒。它在实验室里挖，找到罪魁祸首：em dash。如果回复的 markdown 里有任何非 Latin-1 字符，比如 em dash 或弯引号，V8 就把整个字符串存成 UTF-16，于是每个语法高亮正则都走它更慢的双字节路径。Claude 用一个二十行的改动修掉它：高亮之前把每个代码块拷进一个单字节字符串。

    高亮页面上第一个代码块

    到第二周，我们几乎没法把产出总结进日报了。最忙的日子，两百多个变更落地。Claude 不断提出新 benchmark；约三分之一的 PR 带额外遥测或护栏，每个新埋点又生出更多 thread 和更多机会。

    在一个 channel 里工作意味着一切都在明面上。我们进出彼此的 thread，争论决策、庆祝赢下。消息传开：其他团队开始把自己的变更带进 channel，让性能被审。因为引进的那些护栏和 Claude skills，新项目的写法都微妙地更性能友好。

    护栏

    我们为这个节奏做过准备。因为我们碰的东西几乎全是热路径（first paint、composer、transcript），安全机制是提前建好的。每个 PR 都过 automated review 且至少一个人工批准，单元测试永远先于优化，任何可能引起用户可见问题的东西都放在短命 feature flag 后面发布。

    flag 开始堆起来时，我们开了一个 thread 协调它们的上线和清理。Claude 把每个 flag 分类为 kill switch 或 ramp，一安全就退役它。两周里我们引入了近两百个 flag，超过一半在结束前已清理掉。

    我们也很清楚，性能收益在快速演进的代码库里会衰减，而且 Anthropic 的代码发得很快。一个项目证明了收益，我们就投入去保护它。比如静态 composer，它天生脆弱。我们几乎立刻给用户展示页面的 HTML 副本，然后让 React 直接画在它上面。

    React 渲染哪怕差一个像素，魔法就没了。所以 Claude 建了几十道护栏：

  • 静态 markup 由在 jsdom 里渲染真实的 React 组件生成，一个测试保证它们永不漂移。
  • 一个集成测试套件在十四个 viewport 尺寸下把静态页和 React 渲染对比，断言对齐误差不超过 1 px。
  • 一个按键测试直接打穿 handoff，任何丢失或乱序的键都会让它失败。
  • 线上，每次 handoff 按十分之一像素报告 shift。任何有非零移动的 event，Claude 都会开 thread。

    • 实验室抓不住所有东西，所以我们还用上了最古老的护栏：增量上线。高风险变更先给员工，再给 1% 用户，再给所有人。内部发布静态 composer 四小时后，一位队友分享了一段录屏，里面是一个我们任何指标都看不到的 layout shift。他在新标签页打开 claude.ai 时，composer 会往下掉——但那是我们的代码之外的原因。

    接下来是什么
