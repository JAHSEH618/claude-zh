任务的成本，以及重试的成本

你出发不是为了买几百万 token。你出发是为了做一个功能、完成一次迁移、跑一个任务。token 数只是模型走到那里需要的量。

两个每 token 价格相同的模型，在同一个任务上的花费可能差很多。一个把代码读一遍。另一个读一遍、试个修复、再读一遍。这些每一步都是回合，每个回合重发到目前为止的对话。所以需要的回合多的模型更贵，哪怕单价一样。

读完这篇，你应该能回答关于你自己工作的三个问题：

  • 我的典型任务在 Opus 5.5 上花我多少？
  • 哪些设置会改变它，改多少？
  • 我怎么查自己 session 的用量？

    • 想先说清的权衡是：每种少花 token 的方式都可能让你失去一个做完的任务。更低的 effort、更小的模型、更少的 context，都确实省 token。一次重试比这些省下的更贵。这篇试图给每个权衡标个价。

    这里的数字有些是 list price，有些是从它们推出来的示意。图都是交互的，读的时候改改输入。这些都是尽力而为的示意，一定要查我们的文档和你自己的算账。

    一个任务要花多少？

    Claude Code 里的任务是一个循环。模型读对话、调工具、读结果，再绕一圈，直到做完。每绕一圈是一个 request。循环的成本由四样东西决定。

    回合数。每个回合重发到目前为止的对话。回合越少，处理的输入越少。

    缓存读取。回合重发的内容大部分是模型上一个回合见过的文本。它按 cache read 计费，是输入价的一小部分。

    输出 token 类型。最贵的 token，是输入价的五倍。Thinking 按输出计费，所以走到答案路上推理更少的模型更便宜。

    模型。每个模型有自己的价格，列在定价页上，你选哪个模型就定了每个 token 的价格。

    我们的例子用 Opus 5.5 API list price：输入每百万 token $4，输出 $20，缓存读取 $0.20。和下面的计算器一样，例子把缓存输入按读价计费，其余按输入价，不算缓存写入。token 数是示意。

    回合数

    假设一个任务从 20K token 的 context 开始，随着模型读文件和工具结果长到 120K。40 个回合，平均每个回合发约 70K token。这个任务大约 2.8M 输入 token，尽管对话从没超过 120K。90% 从缓存读的话，输入约 $1.62。同样的任务 25 个回合处理约 1.75M token，输入约 $1.02。

    一个回合的花费超过它新增的 token，因为它重发它前面的一切。所以最便宜的回合是你不需要的那个。

    一个能减回合的习惯是给模型一个检查自己工作的办法。比如一个可跑的测试、一个构建、或一个调端点的脚本。能自查的模型更早发现自己错在哪。

    一遍就收齐所需、把工具调用批量发的模型，重发付得也更少。

    缓存读取

    同样 2.8M 输入 token，一个都不走缓存要花 $11.20。90% 命中率花 $1.62，96% 约 $0.99。没有其他设置对输入成本影响这么大。稳定的 session 自己就能保持高命中率。这篇后面讲几个会打断你缓存的动作，要避开。

    输出 token

    Opus 5.5 上一个输出 token 是一次缓存读取的 100 倍贵。典型任务的 60K 输出 token 花 $1.20，等于从缓存读 6M token。输出包含 thinking。即使 Claude Code 只给你看摘要，你为它全部付费。这就是为什么 effort——它主要改变模型思考多少——那么大地改变账单。

    模型

    缓存读取更便宜的模型主要帮长 session。输出更便宜的模型主要帮需要大量推理的任务。

    OPUS 5.5 变了什么

    变了两样：价格，和模型干多少活。

    每一条价格线都降了。输入输出 token 比 Opus 5 便宜 20%。缓存读取便宜 60%。输入价降，读率跟着降，从输入价的十分之一降到二十分之一。图 A 按每百万 token 对比两个模型。这是 API list price。Pro、Max 或 Team 套餐上，Opus 5.5 更低的价格传导到你的额度里，包括缓存 context，所以额度比 Opus 5 多用约 25%。缓存读取的额外降幅是 API 价格变更。

    另外，Pro、Max、Team 和按席位的 Enterprise 套餐的五小时额度提高了，符合条件的订阅者可以选择使用一次额度重置。在 web 端或 Claude Desktop 的 Settings > Usage 里能找到，终端里的 Claude Code 里没有。重置对整个账户生效，Claude Code 也包括在内。

    用 API key 时，缓存读取的降价对 Claude Code 影响最大。长 agentic session 的输入大部分花在缓存读取上。在下面图 B 计价的那个 session 里，缓存一行从 $1.00 降到 $0.40，是账单上最大的降幅。

    你省多少取决于你工作的形状。一个大部分是缓存读取的 session，输入最多省 60%。一个没有缓存、答案很长的短问题，最多省 20%，因为输出占了大头。大多数 Claude Code 任务在两者之间。下面的计算器显示你的位置。

    你可能看到过 Opus 5.5 运行成本比 Opus 5 低 40% 的说法。这是我们对按 token 计费的典型负载、默认设置下的估计。它假设除了价格更低，Opus 5.5 在 medium 默认下每个任务用的 token 也更少，所以不是 token 单价降 40%。token 价格见图 A，图 B 显示价格变更单独的作用。

    Opus 5.5 在一个答案上可能用更多 token，因为它回复前总是先思考。我们预期人们在 Opus 5.5 上能完成更多，但它因任务而异，在你自己的工作上去量。图 C 对比两个模型每任务的成本。这部分对你的依赖远大于对价格的。

    范围明确的任务上，两个模型大约用同样多的回合完成，你拿到的就只有降价。差距应该在开放式任务上最大，那里模型可能花很多回合在一个错误思路上。没有单个数字适用于每个代码库，去量（看最后一节）。

    长运行以报告收尾。Opus 5.5 结束长运行时交代改了什么、发现了什么、需要你给什么。这也省钱，因为看得到发生了什么，你重跑 session 的次数更少。

    图 B 用相同的 token 数在一个 session 上给两个模型计价。所以差异只有价格变更，别的没有。切换模型对比。token 数是示意。

    一次录制的运行加入第二个效应：模型干活量的变化。有假起头的任务上，差距应该拉大。

    试试你自己的数字

    设你一个任务实际用的量，或从预设开始。预设挺示意，但我仍建议自己做算账。缓存输入按缓存读价计费，新输入按输入价，所以缓存滑杆显示差距里有多少来自缓存读取。

    要用真实 session 填滑杆，任务结束跑 /usage。Session 块给输入、输出和缓存的数字。最后一个滑杆是你关于 Opus 5.5 在你的任务上少干多少活的假设。只看价格变更就留 0%。要用自己的活设它，这样：同一个任务在 Opus 5 和 Opus 5.5 上各跑一遍，比较回合数和输出 token。Measure it yourself 一节带你走一遍，Reading a session 一节显示在 /usage 里查什么。

    把 session 价值最大化的技巧

    Opus 5.5 更低的价格让每个 token 更便宜。怎么跑 session 决定你用多少 token，这些步骤有用。

    换模型之前先升 effort

    Effort 给模型每回合花多少 token 定一个总体倾向：它的 thinking、它写的文本、它的工具调用。effort 低时工具调用更少、更短。Opus 5.5 有四档（low、medium、high 和 xhigh），外加单个 session 可用的 max。下面选一档，看什么时候用它、用什么命令设置它。

  • /effort medium
  • /effort status
  • /model
  • /usage

    • Claude Code 给每个模型设默认档，/effort status 显示你的。范围明确的日常工作试 medium。medium 卡住试 high。它每回合比 medium 花得多，但比换更大的模型少。机械活（比如重命名、把已知模式套到一批文件上）用 low。

    Opus 5.5 默认 medium，比 Opus 5 默认的 high 低一档。同一档在不同模型上不是同样的思考量。给定档位上，Opus 5.5 每回合想得比 Opus 5 多，xhigh 和 max 上最明显。所以别照搬你为 Opus 5 选的档。从 medium 开始，xhigh 和 max 留给量过增益的活。

    effort 计价的一个粗算方式：假设 high 在一个任务上多加 20K thinking token。Opus 5.5 上那是 $0.40。一个 10 回合的重试循环，100K 缓存 context，总共 10K 输出 token，花得差不多。所以省下一次重试的任务上，high 收回成本。medium 一遍能做完的任务上，它白花。

    medium 只修一层时

    你需要更多 effort 最清楚的信号，是修复停在一层。

    假设一个字段在 API handler 里改了名。medium 下，模型更新 handler，handler 的测试通过，客户端还在发旧字段。它做了被要求的事。只是没读得足够远，找不到第二个调用方。high 下，它写之前花更多回合读调用点，一遍改两层。

    一道检查也能抓同一个 bug。模型能跑一个穿过客户端的测试，medium 下旧字段在它写下的那个回合就会挂掉那个测试。所以升 effort 之前，先查模型有没有办法自查工作。跑一次测试花一个回合和它的输出。更多 effort 是每个回合都加 thinking。

    升 effort 档、加检查都不行，就换更大的模型。

    session 中途改 effort

    Claude Code 里跑带档位的 /effort，比如 /effort high。/effort status 打印当前档位。任务中途可以改，新档从下一个 request 生效。

    Opus 5.5 上用 API key 或 Claude 订阅，改 effort 保住缓存。可以为一个难步骤升上去，再降下来，不用重写对话。在 Amazon Bedrock、Google Cloud 的 Agent Platform 或 Claude apps gateway 上，改 effort 仍会清掉缓存的对话，下一个 request 对全部内容付缓存写入价。Opus 5.5 的 thinking 永远开着，没有 thinking 设置可改。

    为你的工作选对模型

    模型选择定了一个 session 里每个 token 的价格，所以它比 effort 更大地移动账单。它的辐射也更远：每个继承主模型的 subagent 也继承它的价格。大多数日子需要三个模型：查东西用小模型，你盯得紧的活用 Opus 5.5，最难的活用更大的。

    Opus 5.5 当日常主力

    你盯着的活用 Opus 5.5：跨几个文件的功能开发、调试、带后续编辑的 code review。你读它做了什么，它跑偏时介入，循环保持短。

    向上换 Fable 5.1

    结果比 token 价格更重要的时候，向上换 Fable 5.1。比如你不会盯着的长运行、代码库里没有现成模式的问题、要协调很多 subagent 的大改动。别等第三次失败。Opus 5.5 配 xhigh 两次撞上同一个问题就换，解决了再换回来。交互式工作 Opus 5.5 更合适，延迟低、更便宜。

    Fable 5.1 list price 是输入每百万 token $10、输出 $50，Opus 5.5 价格的 2.5 倍。它的缓存读取每百万 $0.25，只有 Opus 5.5 价率的 1.25 倍，因为按它输入价的 0.025 倍计费。所以差距在长且缓存重的运行上最小，在写很多内容多的任务上最大。

    在自然断点切换。缓存属于上一个模型，预期新模型第一个回合对整段对话付写入价。先跑 /compact，或带着一份短书面计划开新 session，让那个回合小一点。跑 /model 加别名或模型名切换。/model 还把选择存为新 session 的默认，难的部分做完就换回来。

    向下换做查询

    向下换 Sonnet 或 Haiku 是查东西，不是写代码：搜索和总结的 subagent、读日志和测试输出、"这在哪定义"的问题。跨很多文件的机械编辑，留 Opus 5.5 配 low effort。编辑留在写你其余代码的那个模型上，每回合成本更低。

    要把 subagent 放小模型，在它的定义里设 model: haiku 或 model: sonnet。要把所有 subagent 放一个模型，设 CLAUDE_CODE_SUBAGENT_MODEL 环境变量。subagent 定义里写了模型名，覆盖变量。没有模型设置的 subagent 跑在你的主模型上，除非变量设了。

    每个 subagent 在自己的 context window 里跑，交回一个摘要，它的文件读取不进你的主对话。它仍为自己 token 付费，模型设置决定那笔花费值多少。

    Agent teams 是实验功能，把这一切乘起来。每个队友是独立的 Claude Code 实例，有自己的 context window，退出前一直用 token。我们的 costs 文档 估了队友跑 plan mode 时一个 team 约等于标准 session 七倍的 token。team 保持小，每个任务自包含，队友那部分做完就关。

    权衡是：小模型读错一个搜索结果，把主模型引去追错的文件，绕路的主模型买单。小模型留给错了好发现的活，比如找文件、跑测试、读日志。

    判断类的留给主模型。opusplan 别名用另一种方式分活：Opus 在 plan mode 里做计划，Sonnet 执行计划。那把代码编辑放到 Sonnet 上，和上面的建议相反。做默认之前，在你自己的任务上量一量。

    迁移时检查你的 prompt

    为旧模型写的指令会让 Opus 5.5 写更多、重复工具调用。在 Claude Code 里跑 /claude-api prompt-audit，检查你的 Claude Code 设置（skills、CLAUDE.md 文件等）里有没有这些 prompting 反模式。它也检查你在 Claude Platform 上构建的应用代码。

    我们在一次从 Opus 4.8 到 Opus 5.5 的迁移上测了这个，用的是一个 44 个工单的内部客户支持 benchmark，它的 prompt 带好几个这些模式。换到 Opus 5.5、low effort，benchmark 成本降约 18%。跑 prompt-audit 又降 9%，到比 Opus 4.8 起点低约 25%。audit 移除的是让模型写更多、重复工具调用的仪式性指令：强制的六步流程、scratchpad 规则、验证两遍规则、互相矛盾的指令。

    那个结果来自一个 benchmark，当例子看，别当预期数字。跑完 audit，在真实任务上对比前后的 /usage（见 Measure it yourself）。

    缓存与压缩

    Claude Code 替你处理缓存和压缩。session 怎么跑决定它们省多少。

    缓存怎么工作

    Claude Code 缓存 request 里重复的部分：system prompt、工具定义、到目前为止的对话。

    Opus 5.5 上缓存读取是一个新输入 token 的 5%。写入缓存比新读贵：今天的价格下，五分钟缓存 1.25 倍输入价，一小时缓存两倍输入价。每次命中免费重置寿命。

    Claude Code 里寿命取决于你用什么付。Claude 订阅是一小时。API key 或云厂商默认五分钟，订阅开始从 usage credits 里扣钱后降到五分钟。

    120K token 的 context 下，Opus 5.5 上五分钟写入约 $0.60，读取约 $0.02。一次写入等于 25 次读取。API key 上，六分钟咖啡时间把下一次 $0.02 的读取变成 $0.60 的写入。同样大小的一小时写入约 $0.96，API 上你可以付那个溢价，盖住你一天里的空档。

    session 形状与命中率

    缓存存的是前缀，只能复用 request 里从头和上一次匹配的部分。

    稳定的 session 每个回合在对话末尾追加，命中率保持高。任何改动 request 前面部分的东西都拉低它。改工具定义清掉整个缓存，改 system prompt 从那个点往后清掉，几乎是全部。

    实际里，这些情况预期会有缓存写入：

  • 你暂停超过缓存寿命；
  • 在 Amazon Bedrock、Google Cloud 的 Agent Platform 或 gateway 上改 effort——档位是缓存匹配的一部分；
  • 一个对话里第一次开 fast mode——它改变了缓存匹配的一部分；
  • 连接或断开 MCP server——它会改变每个 request 开始时加载的东西；
  • 切换模型——新模型从空缓存开始；以及
  • 对话被压缩——它重写了缓存匹配的历史。

    • 所以这些在 session 开始时设好，它工作期间别动。

    为什么长 session 每回合更贵

    每个回合重发整个 context，所以 context 增长时每个回合更贵，缓存热着也一样。20K token 的 context，Opus 5.5 上一个回合的缓存读取约 $0.004。150K 时约 $0.03，那个大小 30 个回合光读取就花 $0.90。同样 30 个回合在 20K 约 $0.12。Claude 4.6 及以后模型上，更大的 context window 不改变每 token 价格，成本全部来自重发对话。

    那些 context 很多是早先工作的残留：一小时前的 stack trace、你已经用完的文件、一个你后来修好的测试输出。每个回合仍然把它们全发出去。

    压缩、/compact 和 /clear

    session 接近 context 上限时，Claude Code 总结更早的历史，让后面的回合发得更少。跑 /autocompact 加一个 token 数，可以改那件事发生前 context 多满。

    两个命令让你自己做。/clear 清空对话，不花钱，转到不相关的活时用。/compact 保持连续性，花一个 request。它读要总结的对话，你可以说要留什么，比如 /compact keep the failing test names and the schema change。

    150K token 时压缩的粗价约 $0.25：读取、几千输出 token 的摘要、更短 context 上的一次新缓存写入。之后每个回合在读取上省约 $0.025，所以压缩在约十个回合内收回成本。快做完时的压缩，花的比省的还多。

    那个价格假设缓存热着。缓存热着时，摘要 request 从缓存里读对话，所以压缩要在休息前做，不是休息后。休息超过缓存寿命之后，同一个 /compact 会把整段对话重读一遍再写回缓存。150K token 的五分钟缓存上，光输入就约 $0.75。如果你走了一条想放弃的路，改用 /rewind 回到更早的回合。缓存热着时，那回到的是已经缓存好的前缀。

    摘要也会丢细节。调试 session 中途的压缩可能丢掉那一条要紧的日志行。在自然断点压缩，下一步依赖具体东西时，在 /compact 指令里说明。

    你开始输入之前加载的东西

    你的 CLAUDE.md 文件每个 session 开始时载入 context，所以它的每一行都是每个回合重发内容的一部分。costs 文档建议把它压在 200 行以内。MCP 工具定义是延迟加载的。开始时只加载工具名和 server 指令，工具被用时才加载完整定义。跑 /mcp 看哪些 server 连着，把不用的关掉。

    账单的其余部分

    表格列出影响 Claude Code session 的其他计费规则，有文档的地方附了链接。

    Fast mode 让 Opus 5.5 最快跑 2.5 倍快，价格是标准价的两倍：输入每百万 token $8，输出 $40。Claude 订阅上它计到 usage credits，不算你的套餐额度。你打开它之后的第一个 request，对整段对话付 fast-mode 输入价，不走缓存。所以在 session 开始时开它，别开到一半再开。

    账单计什么 它怎么工作 缓存寿命 Claude Code 里，订阅一小时；API key 或云厂商五分钟，或订阅开始从 usage credits 扣钱后。每次命中重置寿命。API 提供一小时缓存，写入价更高。Costs 文档（Claude Code 寿命）和 prompt caching 文档 缓存写入 今天 API 价格下，五分钟缓存 1.25 倍输入价，一小时缓存 2 倍。Pricing 文档 Thinking 按输出 token 计费，包括没有返回给你的 thinking。Extended thinking 文档 Effort 作用于每个输出 token：文本、工具调用、thinking。Effort 文档 自动压缩 context window 接近上限时运行。/autocompact 加 token 数设阈值。Context window 文档 Subagents 与 agent teams Subagent 在自己的 context window 里工作，交回摘要。plan mode 下的 agent teams 用约标准 session 7 倍的 token。Context window 和 costs 文档 Batch API 经 Message Batches API 发送的 request，输入输出 token 半价。Batch processing 文档 今天的典型花费 平均：跨企业部署约 $13 每开发者每活跃日。90% 的用户，成本低于 $30 每活跃日。两个数字都是当前模型的。公开文档，costs 页（企业均值和 90% 界）

    自己量

    这篇的数字是示意。你的代码库、prompt 和习惯不同，在你自己的任务上量成本。这样查：

  • 在 session 里跑 /usage。/cost 做同样的事。Session 块显示 token 用量和按 list price 估的美元成本。prompt-cache 一行显示你的输入有多少来自缓存。Pro、Max、Team 或 Enterprise 套餐上，同一屏显示你的套餐用量条。美元数字在你机器上按 list price 算，所以订阅上它是你干了多少活的参照，不是账单。
  • 同一个任务跑两遍。Opus 5.5 需要 Claude Code v2.1.280 或更新，先跑 claude update。从你的 backlog 里挑一个，别用玩具例子。用 /model 在 Opus 5 和 Opus 5.5 之间切。记下每次运行的回合数、输出 token 和成本。下结论之前做三四个任务。
  • 团队用 usage 和 cost 报表。Claude Code Analytics API 给每用户的估算成本。Usage and Cost API 按模型、按缓存 token 和未缓存 token 拆花费。
  • 试 effort 阶梯。一个难任务在 medium 跑一遍，再在 high 跑一遍。一个机械任务在 low 跑一遍。

    • 读一个 session

    任务结束时在 /usage 里查三样。

  • 缓存占比。长 session 应该高。低了的话，找一个长暂停、一次模型切换、中途连上的 MCP server，或在云厂商/gateway 上的一次 effort 变更。prompt cache 一行常会点出上次 miss 的可能原因。
  • 输出对输入。小改动配大量输出，通常说明 effort 档对这个任务太高，或者模型在重试。
  • 总输入对对话大小。总量是对话大小的很多倍，session 就走了很多回合，值得读一遍对话找循环在哪重复。

    • 基线的话，Claude Code costs 文档给企业部署平均约 $13 每开发者每活跃日，90% 用户低于 $30 每活跃日。一个 session 花费远超你自己平常水平，值得回头看。

    要记住的

  • 范围明确的日常活用 medium effort。
  • 给模型一个自查工作的办法，跨文件的改动从 plan mode 开始。
  • medium 卡住就把 effort 升到 high。API key 或订阅上，这个改动保住缓存。云厂商或 gateway 上，在断点改。
  • xhigh 两次撞上同一个问题，换 Fable 5.1。解决了换回来。
  • 搜索和读日志的 subagent 放 Sonnet 或 Haiku。代码编辑留在 Opus 5.5。
  • 长 session 保持推进，缓存才热着。
  • 不相关的任务之间用 /clear，断点处 /compact 并注明要留什么。
  • 最重要的一条：每个模型各跑一个真实任务，对比 /usage 报出的数字。自己的数字才是能信的。

    • 希望这篇有用。如果你的额度在 Opus 5.5 上不比 Opus 5 走得远，用 /feedback 告诉我们。
